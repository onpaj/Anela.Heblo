# Weekly Coverage Gap Routine

> **Coupling notice:** This routine depends on two artifacts produced by CI:
> - `coverage-backend` — Cobertura XML files under `./coverage/**/coverage.cobertura.xml`, with `filename=` attributes **already prefixed with `backend/src/`** by the `sed` step at `.github/workflows/ci-main-branch.yml` lines 119–122. If that `sed` step is removed or modified, the routine's module parser will silently produce wrong results.
> - `coverage-frontend` — the single LCOV file at `./frontend/coverage/lcov.info`.
> - Artifact names (`coverage-backend`, `coverage-frontend`) are load-bearing. Renaming either breaks the routine.
> - The `tech-debt` label must exist in `onpaj/Anela.Heblo`. Verified present as of 2026-05-12.

## Purpose

Identify backend and frontend source files with low test line coverage that contain meaningful, untested business logic, and file actionable GitHub issues for the gaps worth closing.

Raw coverage numbers act as a **candidate filter** only. Claude's qualitative judgment — reading the actual source code — is the gate that decides what becomes an issue. The goal is a small number of high-signal issues per week, not mechanical flagging of every file below a threshold.

## Tunable knobs

Two values near the top of the prompt control routine behavior:
- **`COVERAGE_THRESHOLD=60`** — files below this line-coverage percentage are candidates.
- **`MAX_ISSUES_PER_RUN=10`** — maximum issues filed in one run (excess logged as `truncated_due_to_cap`).

## Qualification Rubric

### SKIP (no issue filed) — file matches any of:
- MVC controllers whose action methods only delegate to `_mediator.Send()` or `_mediator.Publish()` with no other logic
- DTO, request, and response classes containing only properties (no methods with logic)
- Startup, configuration, and DI registration code (`Program.cs`, `Startup.cs`, files ending in `Module.cs`, `ServiceCollectionExtensions.cs`)
- Files containing only auto-properties, auto-mapped fields, or trivial passthrough methods
- Generated code (files with `<auto-generated>` headers, known generated paths such as OpenAPI client code)

### FILE (issue created) — file matches any of:
- MediatR handlers (`IRequestHandler`/`INotificationHandler`) with 2+ conditional branches covering validation or business rules
- Domain logic with state transitions, status flows, or invariants
- Business calculations (financial totals, margins, stock quantities, pricing, discounts)
- Error or exception paths whose failure shape (exception type, error code, response payload) is never asserted by an existing test
- Cross-module service contracts where the integration surface is untested

Every candidate (even skipped ones) gets a one-line rationale recorded in the run summary.

## Routine Prompt

The cron registration references this prompt verbatim. To update the routine logic, edit the prompt block below, then update the cron registration via `CronDelete` + `CronCreate`.

```
# Coverage Gap Routine

## Configuration
COVERAGE_THRESHOLD=60
MAX_ISSUES_PER_RUN=10
REPO=onpaj/Anela.Heblo
DRY_RUN=${DRY_RUN:-0}

## Goal
Identify backend and frontend source files with low test coverage that contain meaningful untested logic, and file actionable GitHub issues for gaps worth closing. Raw coverage numbers are only a candidate filter — your qualitative judgment after reading the source code is the gate.

---

## Step 1: Locate Latest Successful CI Run

Run:
```bash
gh run list --workflow=ci-main-branch.yml --branch=main --status=success --limit 1 --json databaseId,headSha,createdAt --repo onpaj/Anela.Heblo
```

Record RUN_ID (databaseId), HEAD_SHA (headSha), and RUN_DATE (createdAt).

If no run is found, OR the run's createdAt is more than 7 days ago, print:
"No successful main-branch CI run within the last 7 days. Filing nothing."
Then exit cleanly (no issues filed, no error).

---

## Step 2: Download Coverage Artifacts

```bash
mkdir -p /tmp/cov-be/${RUN_ID} /tmp/cov-fe/${RUN_ID}
gh run download ${RUN_ID} --name coverage-backend --dir /tmp/cov-be/${RUN_ID} --repo onpaj/Anela.Heblo
gh run download ${RUN_ID} --name coverage-frontend --dir /tmp/cov-fe/${RUN_ID} --repo onpaj/Anela.Heblo
```

After each download:
- If the directory is empty or the download failed: set that side as UNAVAILABLE, note it in the summary, and process the other side independently.
- Backend unavailable → process frontend only (and vice versa).

---

## Step 3: Parse Backend Cobertura XML — Build Candidate List

For each `coverage.cobertura.xml` file in `/tmp/cov-be/${RUN_ID}/`:

Extract `<class>` nodes. For each class node:
1. Read `filename` attribute. It MUST start with `backend/src/` (due to the CI sed step). If it does not, log "WARNING: Unexpected Cobertura path format, skipping: <filename>" and skip.
2. Read `line-rate` attribute (a fraction in [0,1]). Coverage percent = line-rate × 100.
3. Read `lines-valid` attribute. Skip if lines-valid == 0 (no executable lines).
4. Extract module: find the path segment immediately after `Features/` in the filename (e.g. `backend/src/Anela.Heblo.Application/Features/Catalog/GetProductHandler.cs` → module `Catalog`). If no `Features/` in path, module = `Other`.

**Aggregation rule:** Multiple `<class>` nodes may share the same `filename` (one per type in the file). Group by `filename` and aggregate `lines-valid` and `lines-covered` across all nodes before computing file-level coverage. Apply the threshold to the aggregated file-level percentage.

**Cross-layer deduplication:** If the same logical `Features/<Module>/<File>` basename appears in multiple project directories (e.g. Application and Persistence), treat them as one candidate using the first path seen.

Include file in candidate list if file-level line coverage < COVERAGE_THRESHOLD.

---

## Step 4: Parse Frontend LCOV — Build Candidate List

Parse `/tmp/cov-fe/${RUN_ID}/lcov.info` line by line:
- `SF:` → source file path
- `LF:` → lines found (total executable lines)
- `LH:` → lines hit (covered lines)
- `end_of_record` → end of block

For each file block:
- Skip if LF == 0.
- Coverage percent = LH / LF × 100.
- Module = first subfolder under `frontend/src/` in the SF path (e.g. `frontend/src/components/orders/OrderList.tsx` → module `components`).
- Include if coverage percent < COVERAGE_THRESHOLD.

---

## Step 5: Qualify Each Candidate

Process each candidate sequentially (backend first, then frontend):

For each candidate:
1. Use Read to load the full source file at the path found in the artifact.
2. If Read fails (file not found in the runner's checkout), record: `decision=skip, rationale="source not found in checkout"` and continue.
3. Optionally use Grep or Glob to find related test files for additional context.
4. Apply the qualification rubric:

**SKIP (no issue) if the file matches any of:**
- MVC controllers whose action methods only call `_mediator.Send()` or `_mediator.Publish()` with no other logic
- DTO, request, or response classes containing only properties
- Startup, configuration, or DI registration: `Program.cs`, `Startup.cs`, files ending in `Module.cs`, `ServiceCollectionExtensions.cs`
- Files containing only auto-properties, auto-mapped fields, or trivial passthrough methods
- Generated code: files with `<auto-generated>` in their header, or known generated paths

**FILE an issue if the file matches any of:**
- MediatR handler (`IRequestHandler`/`INotificationHandler`) with 2+ conditional branches covering validation or business rules
- Domain logic with state transitions, status flows, or invariants
- Business calculations: financial totals, margins, stock quantities, pricing, discounts
- Error or exception paths whose failure shape is never asserted by any existing test
- Cross-module service contracts where the integration surface is untested

5. Record: `decision` (skip|file), `rationale` (one line explaining why), and if decision==file: `issueTitle` and `issueBody`.

Do NOT paste source code into issue bodies. Describe the untested behavior in plain language.

---

## Step 6: Ensure Label and File Issues

### 6a. Ensure coverage-gap label exists

```bash
gh label list --repo onpaj/Anela.Heblo --json name | grep -q '"name":"coverage-gap"' || \
  gh label create coverage-gap --color e99695 --description "Filed by weekly coverage-gap routine" --repo onpaj/Anela.Heblo
```

### 6b. For each candidate with decision == "file":

**Cap check:** If issues filed this run >= MAX_ISSUES_PER_RUN, record as `truncated_due_to_cap` and stop filing. List remaining qualified candidates in summary.

**Dedup check:**
```bash
SEARCH_TOKEN="<Module>/<basename>"
gh issue list --repo onpaj/Anela.Heblo --label coverage-gap --state open \
  --search "${SEARCH_TOKEN} in:title" --limit 20
```
If a matching open issue exists (title contains the search token), record as `deduplicated` and skip.

**Dry run check:** If DRY_RUN=1, print the issue title and body that would be filed. Skip `gh issue create`. Continue to next candidate.

**File issue:**
```bash
gh issue create \
  --repo onpaj/Anela.Heblo \
  --title "[coverage-gap] <Module>/<File>: <specific untested logic description>" \
  --body "## Module / File
<path>

## Coverage
Line coverage: X% (filter threshold: 60%)

## What's not tested
<Specific description of uncovered branches, conditions, error paths>

## Why it matters
<What could silently break if this logic regresses>

## Suggested approach
<Concrete: unit or integration test, which scenario to cover, ~effort estimate>

---
_Filed by weekly coverage-gap routine on $(date +%Y-%m-%d). Based on CI run #${RUN_ID} (${HEAD_SHA})._" \
  --label "coverage-gap" \
  --label "tech-debt"
```

Record the issue URL.

## Operating Instructions

### Pausing the routine

List current cron entries via `CronList`. Identify the coverage-gap entry. Delete it via `CronDelete <id>`. To resume, re-register with `CronCreate` using the prompt above and schedule `0 4 * * 1`.

### Rerunning manually

Trigger the routine on-demand via the scheduler's manual trigger. For a dry run (no issues filed), set `DRY_RUN=1` in the prompt environment before triggering.

### First-run verification

Before the first live run, perform a dry run: set `DRY_RUN=1` in the prompt, trigger manually, and verify the summary output shows correct artifact discovery, parsing, and qualification without filing any real issues.

### Updating the routine

1. Edit the `## Routine Prompt` section in this file (the source of truth).
2. Delete the existing cron entry via `CronDelete`.
3. Re-register via `CronCreate` with the updated prompt text and schedule `0 4 * * 1`.

### Prerequisites before first live run

1. CI workflow changes (two `upload-artifact` steps) must be merged to `main` and at least one successful CI run must have completed.
2. Verify artifacts exist: `gh run download <run-id> --name coverage-backend` must produce at least one `coverage.cobertura.xml` file.
3. `tech-debt` label must exist in `onpaj/Anela.Heblo` (verified present).
4. `coverage-gap` label is created automatically by the routine on first run.
5. Cron is registered with: model `claude-sonnet-4-6`, allowed tools `Bash,Read,Glob,Grep`, repo `onpaj/Anela.Heblo`, schedule `0 4 * * 1`.
