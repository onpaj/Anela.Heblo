## Findings

### 1. Every Smartsupp frontend hook bypasses the generated typed API client

`frontend/src/api/hooks/useSmartsupp.ts` and all four hooks under
`frontend/src/components/customer-support/smartsupp/hooks/` call the backend through
`frontend/src/api/smartsuppClient.ts`, whose `asInternal()` performs
`apiClient as unknown as { baseUrl; http: { fetch } }` — the exact private-field reach that
`docs/development/api-client-generation.md` forbids in its Enforcement Rules ("**NEVER use
`(apiClient as any)`** to access private fields"). Alongside it, ten response/DTO shapes are
hand-declared even though NSwag already generates all of them.

Verified that **every** endpoint these hooks call has a generated typed method
(`smartsupp_GetConversations`, `smartsupp_GetConversation`, `smartsupp_GetShoptetInfo`,
`smartsupp_GetVisitorInfo`, `smartsupp_CloseConversation`, `smartsupp_RecordPresence`,
`smartsupp_RemovePresence`, `smartsupp_GenerateDraftReply`, `smartsupp_SendMessage`,
`smartsupp_SubmitDraftReplyFeedback`, `smartsupp_GetDraftReplyFeedbackList`) — so nothing here is
blocked on a missing generated method. Two hooks genuinely need status-code branching (409 / 404),
but the document's own escape hatch for that is `getApiBaseUrl()` + `getAuthenticatedFetch()`, not
the internal-transport cast.

### 2. The Smartsupp Application layer talks to `ApplicationDbContext` directly

Four MediatR handlers plus one recurring job in
`Application/Features/Smartsupp/` inject `ApplicationDbContext`. Verified by grep across the whole
Application assembly: only 12 of 1 631 files mention `ApplicationDbContext` at all, and once the
`*Module.cs` DI-wiring files and the two deliberately-documented `Infrastructure/*Adapter.cs`
classes are removed, **Smartsupp's five are the only ones**. `RefreshOrphanContactsHandler` injects
`ISmartsuppRepository` *and* the raw `DbContext` in the same constructor, which shows the
abstraction exists and is being stepped around.

The one abstraction the audit sub-slice does have, `ISmartsuppWebhookAuditWriter`, is declared in
the **Persistence** assembly rather than `Domain/Features/Smartsupp/` where every other Smartsupp
contract lives, and `SmartsuppWebhookController` is the only controller in the API project taking a
feature dependency on `Anela.Heblo.Persistence`.

### 3. `SmartsuppRepository` (Persistence) makes outbound Smartsupp REST calls

`SmartsuppRepository` injects `ISmartsuppApiClient` and calls it from inside
`UpsertConversationAsync`, so a database write silently performs third-party HTTP I/O. With
`HttpTimeoutSeconds = 30` and a 3-attempt exponential-backoff Polly pipeline, an unhealthy Smartsupp
REST endpoint stalls the webhook write path for tens of seconds. Precedent for the layering rule:
#3731 (`AnalyticsRepository` misplaced in Persistence).

### 4. Eight of eighteen webhook reactions are exact clones

Three distinct behaviours are spread across eight classes with byte-identical `HandleAsync` bodies.
Precedent: #3612, accepted for two identical job classes differing by a constant.
