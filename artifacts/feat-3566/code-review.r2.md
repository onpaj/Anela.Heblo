## Review Result: CHANGES_REQUESTED

### Blocking (correctness)
- `backend/src/Anela.Heblo.Application/Features/Invoices/Services/InvoiceImportService.cs:134` — The r1 fix correctly detaches a *new* invoice (`isNew == true`) from the shared `DbContext`'s change tracker when `ExecuteImportInvoice` fails before its own `SaveChangesAsync`. I independently verified this half of the fix is sound: `BaseRepository.DeleteAsync` (`backend/src/Anela.Heblo.Persistence/Repositories/BaseRepository.cs:76-80`) does only `DbSet.Remove(entity)`; `IssuedInvoiceRepository` does not override the entity-parameter `DeleteAsync`, so the base implementation runs. EF Core's documented behavior is that `Remove()` on an entity in the `Added` state (never saved) transitions it straight to `Detached` without issuing any SQL — so this call never attempts an errant `DELETE` against a non-existent row, and `SaveChangesAsync` itself throwing mid-way (leaving the entity still logically `Added`, since EF only advances entity state after a *successful* save) is likewise safely handled by this same branch.

  However, the fix only covers `isNew == true`. The identical failure mode is still fully open for **existing (re-imported) invoices** (`isNew == false`), and it is not hypothetical — the module registers real transformations (`ProductMappingIssuedInvoiceImportTransformation`, `RemoveDAtTheEndOfProductCodeIssuedInvoiceImportTransformation`, `GiftWithoutVATIssuedInvoiceImportTransformation` in `backend/src/Anela.Heblo.Application/Features/Invoices/InvoicesModule.cs`) that can throw. Walk-through: `GetOrCreateAsync` returns an existing invoice via `IssuedInvoiceRepository.GetByIdAsync` (`backend/src/Anela.Heblo.Persistence/Invoices/IssuedInvoiceRepository.cs:22-26`), which uses a plain (tracked) `FirstOrDefaultAsync` — no `.AsNoTracking()`, unlike every other repository in this codebase. `_mapper.Map(invoiceDetail, invoice)` at line 92 then mutates that tracked entity's properties directly. If anything after that — a transformation in the loop at lines 96-99, or `invoice.SyncSucceeded`/`SyncFailed` — throws, execution reaches the outer `catch` at line 128 with `isNew == false`, so `if (isNew && invoice != null)` at line 134 is skipped: the modified entity is never detached or reverted. Because `InvoiceImportService`/`IssuedInvoiceRepository`/`ApplicationDbContext` are `AddScoped` (confirmed in r1's review) and the same instance is reused across the whole batch loop in `ImportInvoicesAsync`, that stale, partially-mutated entity remains tracked. EF's automatic change detection (on by default) will pick it up as `Modified` on the *next* invoice's `SaveChangesAsync` call (line 124) and silently persist its incomplete/inconsistent field values to the DB — even though this invoice was just reported as `Failed` in `resultDto`. This is the exact same class of bug the r1 fix was written to close, just via the `Modified` path instead of the `Added` path, and the code comment at lines 130-133 ("otherwise it stays tracked... and would be silently flushed by whichever later invoice's `SaveChangesAsync` call runs next") overstates what the fix actually guarantees, since it only guards the `isNew` branch. Fix: in the catch block, when `!isNew && invoice != null`, revert the entity to its pre-mutation state before the next iteration's `SaveChangesAsync` can flush it — e.g. `_context.Entry(invoice).State = EntityState.Unchanged` plus reloading/discarding the mutated in-memory values (or `_context.Entry(invoice).Reload()`), or detach it entirely if a fresh read on next access is acceptable. Note `DeleteAsync`/`Remove()` must NOT be used here — unlike the `isNew` case, this entity has a real, already-persisted DB row, and `Remove()` would mark it for deletion.

### Advisory (cleanup)
- `backend/test/Anela.Heblo.Tests/Features/Invoices/InvoiceImportServiceStateTrackingTests.cs:115-188` — The new regression test (`ImportInvoicesAsync_WithFailureBeforeSaveThenSuccess_DoesNotPersistFailedInvoice`) only exercises the new-invoice (`isNew == true`) leak path. Consider adding a mirrored case: invoice A already exists in the DB, its refresh-map/transformation step throws, invoice B (new or existing) succeeds right after in the same batch — and assert invoice A's row in the DB is unchanged from its pre-import state. This would have caught the gap described above.
