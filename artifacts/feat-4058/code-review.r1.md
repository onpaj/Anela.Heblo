### Advisory (cleanup)
- `backend/src/Anela.Heblo.Application/Features/MeetingTasks/Services/ClaudeMeetingTaskExtractor.cs:79-86` — a transport failure (e.g. `HttpRequestException`) on the *final* retry attempt still falls through to the pre-existing "log error + return empty result" path rather than throwing `MeetingTaskExtractionFailedException`. This is a deliberate, explicitly documented scope boundary from the architecture review (transport failures are a different fingerprint than the `JsonReaderException` this issue targets, and are already retried below this layer by `AnthropicChatClient`'s Polly pipeline), so it is not a regression — just worth keeping in mind if a future caller assumes every extraction failure now surfaces loudly.
- `backend/src/Anela.Heblo.Application/Features/MeetingTasks/UseCases/IngestPlaudRecording/IngestPlaudRecordingHandler.cs:75` — `new IngestPlaudRecordingResponse { Success = false }` doesn't set `ErrorCode`, whereas the sibling `ReimportMeetingTranscriptHandler.cs:101` sets `ErrorCodes.Exception` on the equivalent failure path. Harmless today (nothing calls `FullError()`/`ErrorCode` on this response type), but the two handlers now report the same failure with different granularity.
- `backend/src/Anela.Heblo.Application/Features/MeetingTasks/Services/IMeetingTaskExtractor.cs:12-15` — the interface's `ExtractAsync` has no XML doc noting it can now throw `MeetingTaskExtractionFailedException`; the contract change is only documented on the exception type itself, not at the call-site-facing interface.

## Notes

Reviewed the full diff against `spec.r1.md`'s FR-1–FR-5/NFR-1–NFR-2 and this repo's CLAUDE.md conventions.

- `ClaudeMeetingTaskExtractor.ExtractAsync` now loops up to `MaxAttempts = 3`, distinguishing a transport failure (retried, final-attempt falls back to legacy empty-result contract per an explicit, documented architecture decision) from a content/validation failure (malformed JSON, or JSON with a task whose `Title` is empty/whitespace) — the latter always retried up to the same budget and, if exhausted, raised as `MeetingTaskExtractionFailedException` carrying `AttemptCount`/`LastRawResponse`, with a final `LogError` including the raw response. Retries in between log at `Warning`, not `Error`, so expected in-budget retries don't themselves generate error-level telemetry (FR-3/NFR-2).
- `ExtractEmbeddedJsonObject` (new) does a single-pass, string/escape-aware brace-depth scan to recover a `{...}` object embedded in prose, applied only after a direct parse of the fence-stripped text fails — traced it manually against the new prose-wrapped test case and it correctly isolates the embedded object without being confused by braces/quotes inside a task's `description` field (FR-2).
- Both callers, `IngestPlaudRecordingHandler` and `ReimportMeetingTranscriptHandler`, now wrap the `_extractor.ExtractAsync` call in `try/catch (MeetingTaskExtractionFailedException)`, log with their own request-level context (recording/transcript id + attempt count), and return an explicit failure response instead of persisting a transcript with silently-empty tasks reported as success — confirmed neither handler reaches `AddAsync`/`ReplacePendingTasksAsync`/`SaveChangesAsync` on that path (FR-4/FR-5). `PlaudPollingJob` now tracks a distinct `failed` counter (via `response.Success == false`) alongside `ingested`/`skipped`/`notGenerated` in its completion log, so a caught extraction failure is no longer miscounted as a successful ingest.
- Happy path (valid JSON on the first attempt) returns immediately from inside the loop body with exactly one chat-client call — no added latency vs. pre-existing behavior (NFR-1).
- `MeetingTaskExtractionFailedException` is correctly a `sealed class`, not a record — consistent with CLAUDE.md's DTO rule (exceptions are conventionally classes regardless, and this isn't an OpenAPI-exposed DTO anyway). `ExtractedTask`/`MeetingExtractionResult`/`ExtractionPayload` remain internal domain records, which CLAUDE.md explicitly permits.
