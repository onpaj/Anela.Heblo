# [arch-review] Dashboard: SaveUserSettingsHandler duplicates the lock/provision/load scaffold that IUserDashboardSettingsMutator was designed to encapsulate

## Module
Dashboard

## Finding
`backend/src/Anela.Heblo.Application/Features/Dashboard/UseCases/SaveUserSettings/SaveUserSettingsHandler.cs` (lines 37–41) manually re-implements the exact three-step scaffold that `UserDashboardSettingsMutator` encapsulates:

1. `await _mediator.Send(new GetUserSettingsRequest(), ...)` — provisioning
2. `await using var lockHandle = await _lock.AcquireAsync(userId, ...)` — per-user lock
3. `var settings = await _repository.GetByUserIdAsync(userId)` — load

`IUserDashboardSettingsMutator` (and its docstring) describes itself as "the shared scaffold for `Enable/Disable` tile (and future) mutations", but `SaveUserSettingsHandler` injects `IUserDashboardSettingsRepository` and `IUserDashboardSettingsLock` directly, bypassing the mutator entirely.

The reason is structural: `IUserDashboardSettingsMutator.MutateAsync` takes a single `tileId`, so `SaveUserSettings` cannot use it to atomically update a batch of tiles without acquiring and releasing the lock once per tile — which would break atomicity and cause N redundant provisioning calls.

## Why it matters
- The scaffold has a subtle concurrency invariant (provisioning must happen *outside* the lock because the lock is non-reentrant and `GetUserSettingsHandler` also acquires it). That invariant is now encoded twice, in two files, with no cross-reference. A future author changing the order in one place would not know to update the other.
- `SaveUserSettingsHandler` injects three services (`IUserDashboardSettingsRepository`, `IUserDashboardSettingsLock`, `IMediator`) that logically belong to the scaffold, widening its dependency surface unnecessarily.
- Violates the DRY intent of `IUserDashboardSettingsMutator` — the docstring says "future" mutations should go through the mutator, but the bulk-save case was left out.

## Suggested fix
Add a bulk-mutation overload to `IUserDashboardSettingsMutator`:

```csharp
Task<UserDashboardSettingsMutationResult> MutateBulkAsync(
    string? userId,
    IReadOnlyList<UserDashboardTileDto> tiles,
    CancellationToken cancellationToken);
```

Implement it in `UserDashboardSettingsMutator` using the same scaffold (provision → lock → load → loop), then reduce `SaveUserSettingsHandler` to inject only `IUserDashboardSettingsMutator` and `ICurrentUserService` — four lines of logic instead of the current 40.
