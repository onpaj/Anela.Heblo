# Implementation: persistence-migration-isalldy

## What was implemented

Mapped the new `MarketingAction.IsAllDay` domain property to the database
and generated the EF Core migration that adds the column, with a backfill
that reproduces today's midnight-to-midnight guess so no existing row's
live export behavior changes at the moment this migration runs.

## Files created/modified

- `backend/src/Anela.Heblo.Persistence/Marketing/MarketingActionConfiguration.cs` — added `builder.Property(x => x.IsAllDay).IsRequired();` directly after the `EndDate` mapping.
- `backend/src/Anela.Heblo.Persistence/Migrations/20260921072408_AddIsAllDayToMarketingAction.cs` — generated by `dotnet ef migrations add`; `Up()` adds the `IsAllDay boolean NOT NULL DEFAULT false` column then runs the backfill `UPDATE` (rows with midnight-to-midnight `StartDate`/`EndDate` get `IsAllDay = TRUE`); `Down()` left as scaffolded (plain `DropColumn`).
- `backend/src/Anela.Heblo.Persistence/Migrations/20260921072408_AddIsAllDayToMarketingAction.Designer.cs` — generated by tooling.
- `backend/src/Anela.Heblo.Persistence/Migrations/ApplicationDbContextModelSnapshot.cs` — regenerated by tooling to include `IsAllDay`.

## Tests

No new test files for this task (persistence-mapping/migration task, no

## Notes

**EF tooling blocker (transient, resolved without touching scope):** `dotnet ef migrations add` and `has-pending-model-changes` build the *startup* project (`Anela.Heblo.API`, which references `Anela.Heblo.Application`), not just `Anela.Heblo.Persistence`. At this point in the plan, `Anela.Heblo.Application` still has 4 known, out-of-scope compile errors from callers not yet updated to pass `isAllDay` (`CreateMarketingActionHandler.cs`, `UpdateMarketingActionHandler.cs`, `OutlookEventImportMapper.cs` x2) — exactly the call sites the previous task's review already flagged as belonging to `import-mapper-isalldy` and `manual-handlers-isalldy`. To run the EF tooling, I temporarily patched those 4 call sites in memory (adding the same `isAllDay:` argument those later tasks will add for real — `evt.IsAllDay` for the import mapper, `MarketingAction.ComputeIsAllDay(...)` for the two manual handlers), ran `migrations add` and `has-pending-model-changes` against the now-compiling solution, then reverted those 4 files with `git checkout --` before committing. Confirmed byte-for-byte identical to the pre-patch originals via `diff` before and after. Nothing from those files is part of this commit — only the persistence files listed above.

- Also needed to install `dotnet-ef` (pinned to 8.0.8, matching the project's `Microsoft.EntityFrameworkCore` package version) as a global tool, and set `DOTNET_ROOT=/usr/local/dotnet` plus a syntactically-valid (non-connecting) `ConnectionStrings__Development` env var to satisfy `DesignTimeDbContextFactory`'s connection-string requirement — the EF tooling never actually needs a live DB connection to scaffold a migration or diff the model, it only needs `DbContextOptionsBuilder.UseNpgsql(...)` to be called with *some* valid connection string. The Hangfire schema-init failure visible in the tool output (connection refused to 127.0.0.1:5432) is an unrelated side effect of `Program.cs` running at design time and is expected/harmless in this sandboxed environment with no local Postgres.
- Per `CLAUDE.md`, this migration is **not** applied to any database from within this task — it will need to be run manually against dev/staging/production after merge (noted again in the commit message).
