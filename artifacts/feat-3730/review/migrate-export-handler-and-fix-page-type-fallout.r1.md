## Judgment on the 3 reported deviations

1. **`item.code!` at the `handleRowExpand` call site (line 269).** Reasonable, in-scope fix. This is a JSX call-site argument, not a change to `handleRowExpand`'s body — the plan's Global Constraints section explicitly forbids touching `handleRowExpand`'s *implementation* (its own manual-fetch anti-pattern is deliberately left as a separate follow-up), but says nothing about the caller-side type fallout from Task 1's `ManufacturingStockItemDto.code` becoming optional. The adjacent `item.productFamily!` non-null assertion on the same line already pre-existed before this commit (confirmed via diff: only `item.code!` was added), so the fix matches established in-file style exactly and is the minimal change needed to fix a genuine `TS2345` compile error. This is squarely within the task's own title ("fix page type fallout") and the Global Constraints' explicit statement that `strict: true`'s all-optional generated DTOs are "a real compile-error source... Task 1 and Task 2 both contain concrete steps to fix every call site this affects" — one call site was simply missed by the plan's enumeration, and the developer's fix is the narrowest possible correction.

2. **Moving `jest.mock("../../../api/client")` from inside `beforeEach` to top-of-file scope.** Correct and necessary. Jest's `jest.mock` calls are hoisted by `babel-plugin-jest-hoist` only when they appear at module top level; a `jest.mock` call written inside a `beforeEach` runs at test-execution time, after the test file's static `import ManufacturingStockAnalysis from "../ManufacturingStockAnalysis"` (and therefore its static `import { getAuthenticatedApiClient } from "../../../api/client"`) has already resolved the real, unmocked module. The developer's diagnosis is technically correct and independently verifiable, and the fix follows the exact precedent already established in Task 1's own test file (`useManufacturingStockAnalysis.test.tsx`, confirmed by reading `artifacts/feat-3730/task-plan.r1.md`'s Step 1: `jest.mock("../../client");` at true top level). The mock's *configuration* (`.mockResolvedValue`) correctly stays inside the `handleExport` describe's `beforeEach` as the plan specified — only the bare hoisting-required `jest.mock(...)` declaration moved. Re-run confirms the new test passes with this fix in place.

3. **Adding `waitFor` to the `@testing-library/react` import.** Trivial, correct, unavoidable — the plan's own Step 7d test code calls `waitFor(...)` twice but the plan's stated Step 1 import line omits it; without the addition the file fails to compile. Not a design decision, just closing a documentation gap in the plan.

None of the three deviations touch code outside this task's stated scope (`ManufacturingStockAnalysis.tsx` and its test file), none change `handleRowExpand`'s manual-fetch body, and none alter FR-5's required behavior (export column set/values, `isExport: true`, no pagination). All are disclosed transparently in the impl summary's Notes section rather than silently made.
