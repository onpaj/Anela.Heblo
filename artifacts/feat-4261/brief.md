## Finding
`RecurringJobConfiguration` inherits `Entity<string>` (which provides the `Id` property) and also declares its own `JobName` property. In the constructor, both are assigned the same value:

```csharp
// RecurringJobConfiguration.cs:59
Id = jobName; // JobName is the primary key
JobName = jobName;
```

The EF Core configuration (`backend/src/Anela.Heblo.Persistence/BackgroundJobs/RecurringJobConfigurationConfiguration.cs`) maps both as separate table columns and creates a unique index on `JobName`:

```csharp
builder.HasKey(e => e.Id);           // PK on Id
builder.Property(e => e.JobName)...  // Separate column, also persisted (lines 22–27)
builder.HasIndex(e => e.JobName).IsUnique()  // Redundant unique constraint (line 53–57)
```

Since `Id == JobName` by invariant, the database has two columns with identical content in every row. The unique index on `JobName` is also redundant — the primary key constraint on `Id` already guarantees uniqueness over the same value.

## Why it matters
- Extra storage per row (two identical varchar(100) columns).
- Redundant index maintained on every insert/update.
- The duplication is invisible in normal usage, which makes it an ongoing source of confusion: queries using `GetByJobNameAsync` filter on `c.JobName`, while the PK lookups use `Id` — yet they always return the same set.
- Violates DRY: a future refactor updating one property but not the other would silently diverge.

## Suggested fix
Remove `JobName` as an EF-mapped column. Keep it as a `[NotMapped]` convenience property (or a computed property that reads `Id`) and update any direct column references in the repository to use `Id`. Drop the `IX_RecurringJobConfigurations_JobName` index in a migration. The `GetByJobNameAsync` query simply filters on `e.Id == jobName` instead of `e.JobName == jobName`.

If the `Entity<string>` base class is the source of naming friction (i.e., `Id` is a poor name for a string job identifier), the more thorough fix is to not inherit `Entity<string>` and use a conventionally-named `[Key] public string JobName` primary key directly.
