## Finding
`DownloadFromUrlResponse` declares three properties as non-nullable `string` using the null-forgiving initialiser `= null!`, but the `Failure()` static factory method in `DownloadFromUrlHandler` never sets them. Any consumer that reads `response.BlobUrl`, `response.BlobName`, or `response.ContainerName` on an error response will get a `NullReferenceException` at runtime.

## Why it matters
The `= null!` null-forgiving initialiser suppresses the C# nullable-reference-type compiler warning, so the bug is invisible at compile time. Any caller — including `FileStorageController.HandleResponse`, logging middleware, or future orchestrators — that reads these properties on an unsuccessful response will throw. The OpenAPI-generated TypeScript client types all three as non-nullable `string`, creating a false API contract.

## Suggested fix
Change the three properties to nullable `string?`. Minimal, surgical:

```csharp
public class DownloadFromUrlResponse : BaseResponse
{
    public string? BlobUrl { get; set; }
    public string? ContainerName { get; set; }
    public string? BlobName { get; set; }
    public long FileSizeBytes { get; set; }
}
```

Callers that already gate on `response.Success` are unaffected. The TypeScript client will correctly model these as `string | undefined`, matching actual runtime behaviour.
