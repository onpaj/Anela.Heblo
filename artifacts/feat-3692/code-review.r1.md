## Review Result: CHANGES_REQUESTED

### Blocking (correctness)
- `backend/src/Anela.Heblo.Application/Features/Photobank/Infrastructure/Jobs/PhotobankIndexJob.cs:200-221` — Phase B's per-item "remove stale rule tags, then add new ones" logic reads `GetPhotoTagsByPhotoAndSourceAsync(photo.Id, ...)` and checks `PhotoTagExistsAsync(photo.Id, tagId, ...)` directly against the database (`PhotobankRepository.cs:297-302` and `:267-271` both run `_context.PhotoTags.Where(...).ToListAsync()/AnyAsync()`), not against the DbContext's local/pending change-tracker state. Within Phase B, `PhotoTag` rows added via `AddPhotoTagAsync` for earlier items in the same batch are only tracked in memory — the single `SaveChangesAsync` for the whole batch hasn't run yet (it runs once, after the loop, at line 223). So when the *same* `SharePointFileId` appears twice as a non-deleted item in one batch (the exact scenario the new test `UpsertPhotoBatch_DuplicateSharePointFileIdWithinOneBatch_ResultsInSinglePhotoRow` sets up for Phase A, sharing one `Photo` instance via `photosByFileId`), Phase B breaks in two ways:
  1. If the two occurrences match *different* tag names, the first occurrence's freshly-added (but unflushed) `PhotoTag` is invisible to the second occurrence's `existingRuleTags` query, so it is never removed. Both the first item's tag and the second item's tag end up persisted, even though FR-2 requires only the tags recomputed from the *last* processed state of that photo to survive (matches today's per-item-flush semantics, where the second call's `GetPhotoTagsByPhotoAndSourceAsync` would see the first call's already-committed tag and remove it).
  2. If the two occurrences match the *same* tag name, `PhotoTagExistsAsync` also can't see the first occurrence's unflushed insert, so the loop calls `AddPhotoTagAsync` a second time for the same `(PhotoId, TagId)` pair. `PhotoTag`'s primary key is the composite `(PhotoId, TagId)` (`PhotoTagConfiguration.cs:13`), so the batch's `SaveChangesAsync` at line 223 throws a primary-key-violation `DbUpdateException`. Because `root.DeltaLink` is only advanced after the whole item loop succeeds (line 121), and the exception is swallowed by `IndexRootAsync`'s catch-log-continue block, the *next* run re-fetches the identical delta and hits the identical crash — this is a poison-item condition that permanently blocks that root's indexing, not a transient/idempotent retry as NFR-2 assumes.
  No new test exercises the tag-application path for a duplicate `SharePointFileId` within a batch (the existing duplicate test uses an empty tag-rule list), so this gap isn't caught by the suite. Fix: either dedupe `itemMatches` by `Photo.Id` before the Phase B loop (processing each distinct photo's *final* matched tag set once, using the last-seen item's data — mirroring Phase A's last-write-wins collapse), or accumulate pending `PhotoTag` additions/removals for the batch in an in-memory structure keyed by `(PhotoId, TagId)` instead of re-querying the database mid-batch.
