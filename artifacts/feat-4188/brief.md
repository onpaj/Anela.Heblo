## Finding
`PhotobankIndexJob.UpsertPhotoBatchAsync` (lines 240–261 in `backend/src/Anela.Heblo.Application/Features/Photobank/Infrastructure/Jobs/PhotobankIndexJob.cs`) issues two database queries **per photo** inside the per-photo loop:

1. `GetPhotoTagsByPhotoAndSourceAsync(photo.Id, PhotoTagSource.Rule, ct)` — one SELECT per photo to load its existing Rule-source tags for removal.
2. `PhotoTagExistsAsync(photo.Id, tagId, ct)` — one SELECT per (photo, tag) pair to guard against inserting a duplicate.

For a batch of 200 photos with an average of N matching tag rules each, this generates up to `200 + 200×N` extra round-trips per batch call.

The `ReapplyRulesHandler` solves the same problem with a single pre-load: `GetOccupiedTagPairsAsync` loads all non-Rule `(PhotoId, TagId)` pairs in **one** query, then uses an in-memory `HashSet` for constant-time lookups. The same method is already available on `IPhotobankPhotoTagRepository` (line 56 of `PhotobankPhotoTagRepository.cs`).

## Why it matters
`PhotobankIndexJob` runs nightly at 03:00 UTC. A large delta (e.g. after a SharePoint reorganisation) can produce dozens of 200-photo batches. Each batch currently issues O(photos × rules) round-trips for the tag phase, whereas the `ReapplyRulesHandler` design scales to millions of photos with O(1) extra queries. The inconsistency is noted by a comment in the job (`// mirrors ReapplyRulesHandler`) but the mirror is incomplete — the N+1 guard was not adopted.
