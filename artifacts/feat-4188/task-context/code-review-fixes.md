## Blocking findings from code-review.r1.md

- `backend/src/Anela.Heblo.Application/Features/Photobank/Infrastructure/Jobs/PhotobankIndexJob.cs:246` — `UpsertPhotoBatchAsync` now calls `_photoTagRepository.GetOccupiedTagPairsAsync(scopeToTagName: null, ct)` **unscoped**, once per 200-photo batch. `GetOccupiedTagPairsAsync(null, ...)` (see `PhotobankPhotoTagRepository.cs:56-67`) runs `_context.PhotoTags.Where(pt => pt.Source != PhotoTagSource.Rule)` with no photo-ID filter at all — it loads every non-Rule `(PhotoId, TagId)` pair in the **entire table**. `UpsertPhotoBatchAsync` itself is called once per batch inside `IndexRootAsync`'s `foreach (var item in delta.Items)` loop (call sites at lines 102, 119 and 128), so for the exact scenario `spec.r1.md`'s own Background section calls out — "A large backlog (e.g., after a SharePoint reorganisation) can produce dozens of such batches in a single run" — this fix does a full, unfiltered scan-and-transfer of the whole non-Rule `PhotoTags` table *dozens of times in one run*, once per batch, regardless of batch size.
  This directly contradicts `arch-review.r1.md`'s Decision 1, which explicitly considered this exact tradeoff and chose photo-ID scoping specifically to avoid it: *"`ReapplyRulesHandler` can afford an unscoped, `scopeToTagName`-only query because it runs standalone over the whole table; `PhotobankIndexJob` runs nightly against a table that only grows, so an unscoped `GetOccupiedTagPairsAsync` call would itself become an unbounded full-table scan — reintroducing a scaling problem one level up."` `design.r1.md` relaxed that decision to "implementation detail," conditioned on the developer profiling current `PhotoTags` row count first and only reusing the unscoped call if that profiling showed it acceptable — no such profiling is recorded anywhere in `impl/refactor-upsertphotobatch-tag-reconciliation.r1.md`, `impl/full-validation-and-cleanup.r1.md`, or either task's review file.
  It also violates `spec.r1.md`'s own NFR-1 acceptance criterion — "matching the query profile of `ReapplyRulesHandler`" — since `ReapplyRulesHandler` calls this method **once per whole run**, not once per 200-photo batch; here the *count* of queries per batch is O(1) as required, but each query's **cost is O(table size)**, repeated **O(batches)** times per run, so total work for a large backlog run scales as `O(batches × table_size)` — worse than the pre-fix per-photo/per-pair pattern once the table and backlog both grow, which is precisely the scenario this issue was filed to fix.
  Fix: hoist the non-Rule occupied-pairs preload out of the per-batch method so it executes once per `IndexRootAsync` run (e.g., load it once before the `foreach (var item in delta.Items)` loop and pass it into `UpsertPhotoBatchAsync`), or add a photo-ID-scoped overload/parameter to `GetOccupiedTagPairsAsync` (as `arch-review.r1.md` Decision 1 originally specified and as `RemovePhotoTagsBySourceAsync`'s existing `IReadOnlyList<int> photoIds` convention already models) so each batch's query cost is bounded by batch size, not table size. Either approach restores the "O(1) *and bounded-cost* queries per batch" guarantee NFR-1 requires; the current code only satisfies the query-count half of that requirement.
  Note: none of the new/updated tests catch this — `UpsertPhotoBatch_MultipleDistinctPhotosInOneBatch_CallsBulkTagQueriesExactlyOnceEach` only exercises a single `UpsertPhotoBatchAsync` call (one batch), so `Times.Once` there says nothing about the multi-batch-per-run cost multiplication described above.
