## Verification notes (round 1 fixes)

1. **`ChangeTracker.Clear()` safety** — verified safe at both call sites. `giftPackage` (the BOM/ingredient detail) is fetched via `GetGiftPackageDetailAsync` *before* `ExecuteInTransactionAsync` is invoked in both `CreateManufactureAsync` (service.cs:149) and `DisassembleGiftPackageAsync` (service.cs:229), and is a plain DTO (`GiftPackageDto`/`GiftPackageIngredientDto`) built by copying scalar fields out of `IManufactureClient`/`ILogisticsCatalogSource` results — not an EF-tracked entity. It is read again inside the delegate (`giftPackage.Ingredients`) on every attempt, including retries, with no dependency on EF tracking state. `StockUpProcessingService.CreateOperationAsync` (the other in-transaction writer) also constructs a brand-new `StockUpOperation` on every call rather than reusing anything tracked earlier. No navigation property or pre-loaded entity is silently nulled out by the `Clear()`.
2. **Rollback correctness without explicit `catch`** — confirmed. `await using var transaction = await Context.Database.BeginTransactionAsync(ct)` guarantees `DisposeAsync` rolls back an uncommitted transaction, covering: the delegate throwing (log/stock-op `SaveChangesAsync` failure), cancellation via `ct` at any point, and `CommitAsync` itself throwing — in all cases the original exception propagates unchanged since no `catch` intercepts it. This is exercised directly by `GiftPackageManufactureAtomicityIntegrationTests` (`*_SaveChangesFailsOnFinalOperation_RollsBack...`), which asserts zero rows survive after a mid-transaction failure against a real Postgres instance.
3. **Per-attempt token threading** — confirmed. `strategy.ExecuteAsync(async ct => {...}, cancellationToken)` uses the `Func<CancellationToken, Task<TResult>>` overload, so the caller's token drives the retry/backoff loop while the per-attempt `ct` supplied by `PollyExecutionStrategy`/Polly is threaded into `BeginTransactionAsync(ct)`, `operation(ct)` (which threads it further into `AddAsync`/`SaveChangesAsync`/`CreateOperationAsync`), and `CommitAsync(ct)`. Nothing captures the outer `cancellationToken` where the per-attempt token is required.
4. **Retry + stale tracked state (the actual bug that motivated fix #1)** — the new `CreateManufactureAsync_TransientFailureOnFinalSave_RetryCommitsExactlyOneConsistentSet` test is a genuine regression test for this: it fails a transient (retryable) exception on the 4th `SaveChangesAsync` of attempt 1, and asserts the retried attempt commits exactly 3 `StockUpOperation` rows all referencing the *new* log's id — i.e., no orphaned `StockUpOperation` left over from attempt 1's rolled-back log survives. Per the build-validation artifact this test passes against real Postgres.
