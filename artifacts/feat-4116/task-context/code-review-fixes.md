## Blocking findings (verbatim from code-review.r1.md)

### Blocking (correctness)
- `backend/src/Anela.Heblo.Persistence/Repositories/BaseRepository.cs:112` — The delegate is re-run by a *retrying* execution strategy, but the `DbContext` change tracker is never reset between attempts, so a retry writes corrupt data. `PollyExecutionStrategy` really does retry (`DbResilienceOptions.MaxRetryAttempts = 3`, `TransientErrorClassifier.IsTransient` covers `08xxx`, `SocketException`, `TimeoutException`/`TimeoutRejectedException`, `IOException`). The delegate here issues **four** `SaveChangesAsync` calls; each successful one calls `AcceptAllChanges`, flipping its entities `Added → Unchanged`. If attempt 1 fails transiently on save #3 or #4, the transaction rolls those rows back in the DB, but in the tracker they are still `Unchanged` — so attempt 2 will **never re-insert them** — while the entity of the *failed* save is still `Added` and **will** be inserted by attempt 2's very first `SaveChangesAsync`, carrying the stale `SourceId`/`ManufactureLogId` of the rolled-back log. Concretely, a transient failure on the final output stock-up leaves attempt 2 committing an orphan `StockUpOperation` with `DocumentNumber = GPM-{oldLogId:000000}-…` / `SourceId = oldLogId` pointing at a log row that will never exist (the log link is by convention, not an FK — see spec Data Model), which is exactly the `NFR-3` invariant this feature is meant to establish; in the ingredient-loop case the leftover `GiftPackageManufactureItem` instead hits FK `23503` and fails the whole retry with a misleading error. The XML doc at line 108 (“a retry re-runs the whole delegate from a clean change tracker”) is factually wrong — EF Core does not reset the tracker across execution-strategy retries — and the same wrong claim in `PollyExecutionStrategy`'s class comment (`backend/src/Anela.Heblo.Persistence/Infrastructure/Resilience/PollyExecutionStrategy.cs:9`, pre-existing) is presumably its source. Fix: reset the context state at the start of *each* attempt (e.g. `Context.ChangeTracker.Clear()` as the first statement inside the `strategy.ExecuteAsync` lambda, before `BeginTransactionAsync`), or make the operation non-retrying and let the caller retry from a fresh scope. Whichever is chosen, correct the XML doc.
- `backend/src/Anela.Heblo.Persistence/Repositories/BaseRepository.cs:117` — The `strategy.ExecuteAsync(Func<Task<TResult>>)` overload is used, so (a) the caller's `cancellationToken` is never handed to the execution strategy — it defaults to `CancellationToken.None`, so an aborted request cannot cancel the retry loop or its backoff delays — and (b) the per-attempt `CancellationToken` that `PollyExecutionStrategy` supplies (the one `AddTimeout(TotalTimeBudget)`, 10 s by default, cancels) is discarded: the lambda takes no token and passes the *captured outer* token to `operation` and `BeginTransactionAsync`. On a timeout, Polly therefore throws `TimeoutRejectedException` (classified transient) and starts attempt 2 **while attempt 1 is still running on the same scoped `ApplicationDbContext` and connection** — a concurrent-use-of-DbContext / interleaved-transaction failure, not a clean retry. Use the token-carrying overload (`strategy.ExecuteAsync(async ct => { … }, cancellationToken)`) and pass that per-attempt `ct` into `BeginTransactionAsync`, `operation(ct)` and `CommitAsync`/`RollbackAsync`.
- `backend/src/Anela.Heblo.Persistence/Repositories/BaseRepository.cs:126` — The `catch { await transaction.RollbackAsync(...); throw; }` block loses the original exception whenever the rollback itself throws — which is precisely the common case here, since the transient errors this strategy exists for (broken connection `08xxx`, `SocketException`, `IOException`) leave the Npgsql connector unusable, and `RollbackAsync` on a broken/completed transaction throws. The replacement exception then propagates instead of the real cause, violating FR-1's acceptance criterion “the exception type/message surfaced to the caller on failure is unchanged”, and it also changes the transient classification `PollyExecutionStrategy` sees. `await using var transaction` already rolls back an uncommitted transaction on dispose, so either drop the `catch` entirely or wrap the `RollbackAsync` call in its own `try { … } catch { /* preserve original */ }`.
