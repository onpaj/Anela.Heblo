## Overall Notes
Verification performed, beyond the orchestrator's `dotnet test` run:

- **Real Postgres, not InMemory:** confirmed via `[Collection("PostgresIntegration")]`, `PostgresSharedContainerFixture.CreateDatabaseAsync`, and raw-SQL `CREATE TABLE IF NOT EXISTS` schema setup for `GiftPackageManufactureLogs`, `GiftPackageManufactureItems`, and `StockUpOperations` — same established pattern as `ChangeTransportBoxStateReceiveAtomicityIntegrationTests`. No `UseInMemoryDatabase` anywhere in the file.
- **`PollyExecutionStrategy` genuinely configured:** `CreateContext()` builds `DbContextOptionsBuilder<ApplicationDbContext>().UseNpgsql(_connectionString, npgsql => npgsql.ExecutionStrategy(deps => new PollyExecutionStrategy(deps, pipelineProvider, metrics, logger)))`, which is the exact same call shape as `PersistenceModule.cs` lines ~100-116. This means `BaseRepository.ExecuteInTransactionAsync`'s `Context.Database.CreateExecutionStrategy().ExecuteAsync(...)` path (FR-3 acceptance criterion (c)) is genuinely exercised, not bypassed with the bare non-retrying strategy the transport-box test uses.
- **`failOnCallNumber: 4` is verifiably the last save for a 2-ingredient BOM.** Traced the call sequence directly from source:
  - `CreateManufactureAsync`: log `AddAsync`+`SaveChangesAsync` (#1) → `CreateOperationAsync` per ingredient, each doing its own `AddAsync`+`SaveChangesAsync` in `StockUpProcessingService.CreateOperationAsync` (#2, #3 for 2 ingredients) → output stock-up `CreateOperationAsync` (#4). Confirmed via `LogisticsStockOperationAdapter.CreateOperationAsync` → `StockUpProcessingService.CreateOperationAsync`, which does exactly one `SaveChangesAsync` per call — no batching.
  - `DisassembleGiftPackageAsync`: log save (#1) → package stock-down `CreateOperationAsync` (#2) → one stock-up `CreateOperationAsync` per component, 2 components (#3, #4).
  - In both cases #4 is the true last write, so the rollback tests prove that already-flushed writes from calls #1–#3 are rolled back together with the failing #4 — not merely that the last write never landed. Non-vacuous.
- **Non-transient failure confirmed correct by design, not just by convention.** `ThrowOnNthSaveInterceptor` throws a plain `InvalidOperationException` with no `PostgresException`/`SocketException` inner exception. I read `TransientErrorClassifier.IsTransient` and `DbResiliencePipelineProvider.BuildPipeline` (`ShouldHandle = new PredicateBuilder().Handle<Exception>(TransientErrorClassifier.IsTransient)`): a bare `InvalidOperationException` falls through to `_ => false` in `IsTransientCore`, so Polly's retry pipeline does not retry it — the exception propagates on first attempt, exactly as the test expects (`ex.Should().BeOfType<InvalidOperationException>()`), and the retry pipeline cannot mask the failure.
- **Production code untouched.** `git show --stat HEAD` (`f8bf4b311`) shows only the new test file (378 insertions, 0 other files). `GiftPackageManufactureService.cs` and `BaseRepository.cs` match the spec's FR-1/FR-2/FR-3 design exactly (fetch BOM before opening the transaction; `ExecuteInTransactionAsync` wraps `CreateExecutionStrategy().ExecuteAsync(...)` + `BeginTransactionAsync`/`CommitAsync`/`RollbackAsync`, never a bare `BeginTransactionAsync`) — no weakening to make the new tests pass.
- **Schema/entity fidelity spot-checked** against `GiftPackageManufactureLogConfiguration`, `GiftPackageManufactureItemConfiguration`, and `StockUpOperationConfiguration`: table names, the `ManufactureLogId` FK name (not `LogId`, per the task's called-out gotcha), column types (`timestamp without time zone` for the log tables, matching `CreatedAt`'s `HasColumnType`), and the `DocumentNumber` unique index all line up with the real EF Core mappings. The test's minimal schema omits a few secondary indexes present in production (`IX_StockUpOperations_State`, `_Source`, `_State_CreatedAt`, `_State_Active`) — immaterial to the atomicity assertions, consistent with the "minimal schema" pattern the task and the existing transport-box test both use.
- **Assertions are non-vacuous and quantitatively verified.** Computed the expected `StockUpOperation` amounts by hand against the BOM fixture (`SetupTwoIngredientBom`: ING001 Amount=2.0, ING002 Amount=1.5) for both quantity 5 (manufacture: -10, -7, +5) and quantity 3 (disassembly: -3, +6, +4) — all match the test's expected values, including the `(int)` truncation of `1.5 * 5 = 7.5 → 7` and `1.5 * 3 = 4.5 → 4`.
