# Code Review: feat-3844 — Atomic and idempotent TransportBox Receive

## Review Result: CLEAN

### Blocking
- None

### Advisory
- **No explicit "mixed partial-idempotency" test at the handler/service boundary.** The spec's FR-2 acceptance criteria explicitly calls out a scenario where "some `DocumentNumber`s exist and others don't" for a single Receive call. `StockUpProcessingServiceTests` covers "exists → skip" and "doesn't exist → create" as two separate single-call unit tests, and `ChangeTransportBoxStateHandlerTests` covers multi-product aggregation with the service fully mocked (so the real pre-check never runs there). Because each `CreateOperationAsync` call is independently idempotent per document number, the mixed case is logically implied by composing the two proven single-call behaviors — but there's no single test exercising "box with 2 products, 1 already has a `StockUpOperation` row, 1 doesn't" end-to-end through the real `StockUpProcessingService`. Not a correctness gap given the logic is call-scoped, just a coverage gap worth a follow-up test if this path gets touched again.
- **`persistImmediately` placed after `CancellationToken` deviates from the .NET convention of `CancellationToken` being the trailing parameter.** This is deliberate and well-justified (avoids touching 4 call sites in `GiftPackageManufactureService.cs`), and is defended with an explicit "Do not reorder this parameter" comment on both `IStockUpProcessingService.CreateOperationAsync` and `ILogisticsStockOperationService.CreateOperationAsync`. Flagging only so a future reviewer doesn't mistake the comment for boilerplate and "clean it up," which would silently flip `GiftPackageManufactureService`'s call sites to positional-argument breakage if a positional bool were ever appended without checking.

## What was verified

**Ordering / atomicity (FR-1).** Read `ChangeTransportBoxStateHandler.Handle` end-to-end (`ChangeTransportBoxStateHandler.cs:56-212`). `HandleReceived` is invoked via the `CallBackMap` dispatch at line 106-114, strictly before `transition.ChangeStateAsync` (126), `_repository.UpdateAsync(box, ct)` (134) and the box's own `_repository.SaveChangesAsync(ct)` (135). `HandleReceived` always returns `null` (no early-return branch), so control always reaches the final `SaveChangesAsync` on the success path. Confirmed `BaseRepository<TEntity,TKey>.AddAsync` (`BaseRepository.cs:57-61`) only calls `DbSet.AddAsync` — stages the entity on the change tracker, no DB round-trip — so nothing is flushed between `HandleReceived`'s staged inserts and the box's own save. Both `TransportBoxRepository` and `StockUpOperationRepository` are constructed over the same injected `ApplicationDbContext`, matching the spec's stated single-scope assumption. No `SaveChangesAsync` call exists anywhere between the staged `AddAsync`s and the box's final save. This is correct.

**CI transaction guard.** Verified `scripts/check-no-managed-tx.sh` exists and greps `backend/src` for `BeginTransaction|UseTransaction`, exiting 1 if found — matches the arch-review's claim and correctly rules out the explicit-transaction alternative given `PollyExecutionStrategy`'s `RetriesOnFailure`.

**Idempotency pre-check race tolerance (FR-2).** `StockUpProcessingService.CreateOperationAsync` now does a `GetByDocumentNumberAsync` DB query before `AddAsync`. This is a check-then-act with a TOCTOU window under true concurrent double-submits (two separate requests/DbContexts racing the same box), which the arch-review and spec both explicitly accept as residual risk (spec FR-2: pre-check is "a safety net, not the primary correctness mechanism"; arch-review Risks table calls this out by name and explains why no `DbUpdateException`-catching fallback was added). Verified the unique index `IX_StockUpOperations_DocumentNumber_Unique` is untouched, so the race cannot produce duplicate rows — worst case is one racing caller's `SaveChangesAsync` throws, falls into the generic catch (`ChangeTransportBoxStateHandler.cs:202-211`), and a subsequent retry succeeds via the now-satisfied pre-check (self-healing, not a permanent wedge). This matches the spec's stated tolerance and is not a regression versus the bug being fixed (which produced permanent wedging, not a single-retry transient failure).

**Call-site compatibility (FR-3).** Grepped all `CreateOperationAsync(` call sites in `backend/src`. `GiftPackageManufactureService.cs` has 4 call sites (`CreateManufactureAsync` x2, `DisassembleGiftPackageAsync` x2), all passing `cancellationToken` positionally as the last argument with no `persistImmediately` — these compile unchanged and continue to get `persistImmediately: true` (immediate commit, today's behavior), confirming the "placed after `ct`" parameter-ordering rationale actually holds in practice, not just in theory.

**Moq test updates.** Checked every changed `Setup`/`Verify` block across `TransportBoxUniquenessTests.cs`, `LogisticsStockOperationAdapterTests.cs`, `GiftPackageManufactureServiceTests.cs`, and `ChangeTransportBoxStateHandlerTests.cs`. The mechanical `It.IsAny<bool>()` additions are all on assertions that were never testing the `persistImmediately` value in the first place (they assert document number, product code, amount, source enum, or call count) — appending `It.IsAny<bool>()` is the correct, precise way to keep matching a 7-arg mock signature without asserting something the test was never about. Critically, the behavior this fix is actually about — `HandleReceived` passing `persistImmediately: false` — is asserted with the literal `false` (not `It.IsAny<bool>()`) in two places: `ChangeTransportBoxStateHandlerTests.Handle_InTransitToReceived_PassesPersistImmediatelyFalse` (new test, asserts `false` is passed to `ILogisticsStockOperationService.CreateOperationAsync`) and `LogisticsStockOperationAdapterTests.CreateOperationAsync_PersistImmediatelyFalse_ForwardsToService` (new test, asserts the adapter forwards `false` to the inner service unchanged). `StockUpProcessingServiceTests` adds three new tests directly against the concrete service with a mocked `IStockUpOperationRepository`, correctly verifying: doc-number-exists → `AddAsync` and `SaveChangesAsync` both never called; doc-number-missing + default → `AddAsync` once, `SaveChangesAsync` once; doc-number-missing + `persistImmediately: false` → `AddAsync` once, `SaveChangesAsync` never. None of these are permissive rewrites that silence a failure — each mechanically-touched assertion still asserts everything it asserted before, plus the new tests assert the one thing that matters (the true/false split) with exact literals.

**No stray `GetByDocumentNumberAsync`-mock gaps.** Confirmed that every test exercising the real `StockUpProcessingService.CreateOperationAsync` (the only concrete-service tests, in `StockUpProcessingServiceTests.cs`) sets up `GetByDocumentNumberAsync` before calling `CreateOperationAsync`; all other touched test files mock `IStockUpProcessingService`/`ILogisticsStockOperationService` at the interface level and never hit the real repository call, so there's no risk of an unmocked `GetByDocumentNumberAsync` returning a Moq default `null` `Task` and NREing.

No correctness bugs, spec deviations, or architecture-guideline violations found. The implementation is a minimal, surgical change exactly as scoped: `HandleReceived`'s pre-existing ordering already put the deferred inserts before the box's save, so the fix genuinely required no reordering — only making the per-call `SaveChangesAsync` conditional and adding the idempotency pre-check, both gated correctly for the one call site that needs the new behavior.
