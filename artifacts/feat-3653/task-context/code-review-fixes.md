## Blocking findings (verbatim from `code-review.r1.md`)

- `frontend/src/api/hooks/useBankStatements.ts:72-75` — The `new Date(request.dateFrom)` → `apiClient.bankStatements_GetBankStatements(...)` → `frontend/src/api/generated/api-client.ts:1636-1642` (`dateFrom.toISOString()`) round-trip changes what calendar date the backend actually receives, depending on the host's local timezone. `new Date('2026-01-01')` parses the date-only string as **UTC midnight**; `.toISOString()` re-serializes it as `"2026-01-01T00:00:00.000Z"`. The backend's `[FromQuery] DateTime? dateFrom` (`backend/src/Anela.Heblo.API/Controllers/BankStatementsController.cs:84`) is bound via ASP.NET Core's default `DateTime` conversion, which — for a string containing a `Z`/UTC designator and no `DateTimeStyles.RoundtripKind` — converts the value to the **server's local time** and returns `Kind = Local`. Verified empirically (`DateTime.Parse("2026-01-01T00:00:00.000Z", CultureInfo.InvariantCulture)`):
  - With `TZ=Europe/Prague` (the timezone pinned in `Dockerfile`/`backend/src/Anela.Heblo.API/Dockerfile`, positive UTC offset) the result is `2026-01-01T01:00:00+01:00` → `.Date` still `2026-01-01`, so production currently "gets away with it" by luck of a positive offset.
  - With a negative-offset host timezone (e.g. `TZ=America/Los_Angeles`, plausible for a developer running the backend locally without the Docker image's `TZ` pin) the same input parses to `2025-12-31T16:00:00-08:00` → `.Date` is **2025-12-31**, one day earlier than the user selected.
  Since `BankStatementImportRepository.GetFilteredAsync` filters on `bs.StatementDate.Date >= filter.DateFrom.Value.Date` / `<= filter.DateTo.Value.Date` (`backend/src/Anela.Heblo.Persistence/Features/Bank/BankStatementImportRepository.cs:52-56`), this off-by-one silently shifts the filtered date range by a day in that scenario — a real regression versus the pre-change behavior, where the raw `YYYY-MM-DD` string was passed straight through and parsed by `DateTime.TryParse` with no timezone reinterpretation at all.

## Required fix approach

Fix this on the **backend**, scoped to only the `GetBankStatements` action's four date parameters — do not touch the other 5 controllers in the codebase that also use `[FromQuery] DateTime?` (`LogisticsController` x2, `SmartsuppWebhookAuditController`, `CatalogController`, `InvoiceClassificationController`, `StockUpOperationsController`); this fix must not change their behavior.

Add a small custom `IModelBinder` (with an `IModelBinderProvider` registered in DI, or applied directly via a `[ModelBinder(BinderType = typeof(...))]` attribute on the four parameters) that parses the raw query-string value using:

```csharp
DateTime.TryParse(value, CultureInfo.InvariantCulture, DateTimeStyles.AdjustToUniversal | DateTimeStyles.AssumeUniversal, out var parsed)
```

This makes the parsed value timezone-independent (always UTC-normalized, ignoring the server's local offset entirely), which fixes the bug at its root regardless of what timezone the server runs in.
