## Review Result: CHANGES_REQUESTED

### Blocking (correctness)
- `frontend/src/api/hooks/useBankStatements.ts:72-75` — The `new Date(request.dateFrom)` → `apiClient.bankStatements_GetBankStatements(...)` → `frontend/src/api/generated/api-client.ts:1636-1642` (`dateFrom.toISOString()`) round-trip changes what calendar date the backend actually receives, depending on the host's local timezone. `new Date('2026-01-01')` parses the date-only string as **UTC midnight**; `.toISOString()` re-serializes it as `"2026-01-01T00:00:00.000Z"`. The backend's `[FromQuery] DateTime? dateFrom` (`backend/src/Anela.Heblo.API/Controllers/BankStatementsController.cs:84`) is bound via ASP.NET Core's default `DateTime` conversion, which — for a string containing a `Z`/UTC designator and no `DateTimeStyles.RoundtripKind` — converts the value to the **server's local time** and returns `Kind = Local`. I verified this empirically (`DateTime.Parse("2026-01-01T00:00:00.000Z", CultureInfo.InvariantCulture)`):
  - With `TZ=Europe/Prague` (the timezone pinned in `Dockerfile`/`backend/src/Anela.Heblo.API/Dockerfile`, positive UTC offset) the result is `2026-01-01T01:00:00+01:00` → `.Date` still `2026-01-01`, so production currently "gets away with it" by luck of a positive offset.
  - With a negative-offset host timezone (e.g. `TZ=America/Los_Angeles`, plausible for a developer running the backend locally without the Docker image's `TZ` pin) the same input parses to `2025-12-31T16:00:00-08:00` → `.Date` is **2025-12-31**, one day earlier than the user selected.
  Since `BankStatementImportRepository.GetFilteredAsync` filters on `bs.StatementDate.Date >= filter.DateFrom.Value.Date` / `<= filter.DateTo.Value.Date` (`backend/src/Anela.Heblo.Persistence/Features/Bank/BankStatementImportRepository.cs:52-56`), this off-by-one silently shifts the filtered date range by a day in that scenario — a real regression versus the pre-change behavior, where the raw `YYYY-MM-DD` string was passed straight through and parsed by `DateTime.TryParse` with no timezone reinterpretation at all. This directly contradicts NFR-1 ("behavioral compatibility... must be unchanged for currently valid inputs") and FR-5's acceptance criterion of no behavioral change to `ImportTab.tsx` filtering. Fix by avoiding the UTC-instant round-trip for these date-only values (e.g. bind as `DateOnly?` on the backend, or have the frontend send a bare `YYYY-MM-DD` string instead of `Date.toISOString()`, or use `DateTimeStyles.RoundtripKind`/explicit UTC handling in a custom binder so the received date never depends on the server's local timezone offset).

### Advisory (cleanup)
- `frontend/src/api/hooks/__tests__/useBankStatements.test.ts:129-146` — The new "converts dateFrom/dateTo strings to Date objects" test mocks `bankStatements_GetBankStatements` entirely, so it only checks the `Date` object passed into the generated client and never exercises the real `.toISOString()` query-string serialization in `api-client.ts`. It would not have caught the timezone round-trip issue above; consider a test that hits the real generated client's URL-building code (or asserts on the actual query string) to cover this class of regression.
