## Finding
When a scheduled job (e.g. `ComgateCzkImportJob`, `ShoptetPayImportJob`) runs, the staleness warning is emitted twice from two different call sites for the same import run:

   else if (span > _options.StaleWarningDays)

2. `ImportBankStatementHandler.Handle` — `backend/src/Anela.Heblo.Application/Features/Bank/UseCases/ImportBankStatement/ImportBankStatementHandler.cs`, lines 70–77:
   ```csharp
   if (state.LastValidImportDate.HasValue)
   {
       var daysBehind = (DateTime.UtcNow.Date - state.LastValidImportDate.Value.Date).Days;
       if (daysBehind > _watermarkOptions.StaleWarningDays)
           _logger.LogWarning(
               "Bank import watermark is {DaysBehind} days stale for account {AccountName}. Last valid date: {LastValidDate}",
               daysBehind, request.AccountName, state.LastValidImportDate.Value.Date);
   }
   ```

Both blocks check `daysBehind > StaleWarningDays` against the same watermark state. The handler check was presumably added to catch the manual-API trigger path, but it fires on every job-triggered import too.

## Why it matters
- Monitoring / alerting on the staleness warning log message fires twice per job run, creating false double-alerts.
- Two slightly different message formats for the same condition make log aggregation inconsistent.
- The handler has no business knowing whether the watermark is stale — that decision belongs to the orchestration layer (the job).

## Suggested fix
Remove the staleness check from `ImportBankStatementHandler.Handle` (lines 70–77). The job already checks and logs it before sending the request. The handler's responsibility is to execute the import for the given date range, not to evaluate whether that range is overdue.

If the manual-API trigger path also needs the warning, move the check into a shared `BankAccountSettings` extension or into `GetBankStatementListRequestValidator` — but do not duplicate it in both the job and the handler.
