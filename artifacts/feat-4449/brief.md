FileStorage

## Finding
`IBlobStorageService` (Domain layer, `backend/src/Anela.Heblo.Domain/Features/FileStorage/IBlobStorageService.cs`, line 22) declares `DownloadFromUrlAsync(string fileUrl, ...)`. This method signature couples the Domain-level storage interface to external HTTP fetching — the `fileUrl` parameter implies the interface knows about HTTP endpoints, a concern that belongs in the Application or Adapter layer.

The result is an awkward split: `DownloadFromUrlHandler` (Application, line 51–66) does its own HTTP HEAD probe via `IHttpClientFactory`, and then calls the same `IBlobStorageService.DownloadFromUrlAsync`, which also creates an HTTP client (`AzureBlobStorageService`, lines 39–43) to perform the GET. HTTP download logic is spread across two layers.

Pure storage operations that belong on `IBlobStorageService` (Domain): `UploadAsync`, `DownloadAsync`, `DeleteAsync`, `GetBlobUrl`, `ExistsAsync`, `ListBlobsAsync`, `ListVirtualDirectoriesAsync`.

The "download from URL → upload to blob" composite operation belongs entirely in the Application layer — `DownloadFromUrlHandler` already orchestrates it with HEAD probe + retry pipeline.

## Why it matters
Domain interfaces must not depend on Application or Infrastructure concerns (Clean Architecture). Defining `DownloadFromUrlAsync` in Domain means the Domain layer is aware of and coupled to external HTTP fetching. The concrete `AzureBlobStorageService` adapter has to implement HTTP logic to satisfy a Domain contract, which it does via `IHttpClientFactory` — an Application-registered named client. This is a Domain→Infrastructure dependency in disguise.
The split also means a single logical download operation has its retry logic (`DownloadResilienceService`) in Application but its actual HTTP call inside the Domain interface implementation, making the flow hard to follow and the retry boundary opaque.

## Suggested fix
1. Remove `DownloadFromUrlAsync` from `IBlobStorageService`. `IBlobStorageService` becomes a pure blob-store contract: upload stream, download stream, delete, exists, list, get URL.
2. The `AzureBlobStorageService` drops its `IHttpClientFactory` dependency and its HTTP download code.
3. `DownloadFromUrlHandler` owns the full composite flow: create `HttpClient`, stream-download, stream-upload via `IBlobStorageService.UploadAsync`. The handler already has `IHttpClientFactory` for the HEAD probe, so this is additive, not new infrastructure.
4. `FileStorageConstants.FileDownloadClientName` moves from Domain to Application (e.g., into `FileStorageModule`), removing the only Domain constant that leaks an HTTP infrastructure name.
