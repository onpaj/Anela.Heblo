## Why it matters
These are business-domain facts (Shoptet's order lifecycle state IDs) expressed twice. A silent drift between the two copies will produce a state-transition bug that only surfaces at runtime under the specific configuration path that exercises the stale copy. The duplication violates KISS — there is no behaviour difference between the two request types' defaults that justifies the duplication.

## Suggested fix
Remove the constants from `PrintPickingListRequest` and reference them from `ExpeditionPickingRequest` via the existing `LogisticsExpeditionPickingAdapter`, or — if the Logistics module should not depend on ExpeditionList contracts — move the shared state ID constants to a single shared location (e.g. `ExpeditionPickingRequest` only, and have the adapter read from the consumer-side constants when building the inner request). Whichever approach is chosen, there should be exactly one declaration for each constant.
