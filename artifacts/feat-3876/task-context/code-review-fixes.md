### Blocking (correctness)
- `frontend/src/components/customer-support/smartsupp/hooks/useGenerateDraftReply.ts:74` — The `catch` around `smartsupp_GenerateDraftReply` unconditionally discards the caught error and always calls `messageForError(undefined)`, producing the generic "Nepodařilo se vygenerovat odpověď." message. But the backend's `HandleResponse` (`BaseApiController.cs`) never returns HTTP 200 with `success:false` — every business failure (400 `SmartsuppConversationEmpty`, 404 `SmartsuppConversationNotFound`, 503 `SmartsuppDraftReplyAiUnavailable`) is returned as a non-2xx status whose JSON body is the `GenerateDraftReplyResponse` itself (`{success:false, errorCode:...}`). For 400/404 the generated client's `processSmartsupp_GenerateDraftReply` parses that body via `ProblemDetails.fromJS(...)` before throwing, and `ProblemDetails`'s blanket `for (var property in _data) this[property] = _data[property]` copy preserves `errorCode` on the thrown object — exactly the mechanism `useSubmitDraftReplyFeedback.ts` (same PR) correctly relies on via `err.errorCode`. This hook throws the generic message anyway instead of reading `(e as {errorCode?:string}).errorCode`, so the specific Czech messages ("AI služba je momentálně nedostupná…", "Konverzace neobsahuje zprávu zákazníka.", "Konverzace nebyla nalezena.") become unreachable in production — a regression against NFR-2's "byte-identical error messages" requirement. The `data.success === false` branch a few lines below, which the new unit test exercises to "prove" these messages still work, can never actually fire since `HandleResponse` never returns 200 with `success:false`.
