## Finding
`MarginCalculator.CalculateAsync` is annotated throughout with `// 🔒 PERFORMANCE FIX` comments claiming a "streaming approach" that "minimizes memory usage". However, the implementation accumulates every `AnalyticsProduct` — including its full `List<SalesDataPoint> SalesHistory` — into the `groupProducts` dictionary:

```csharp
// backend/src/Anela.Heblo.Application/Features/Analytics/Services/MarginCalculator.cs:75-79
groupTotals[groupKey] += marginContribution;
groupProducts[groupKey].Add(product); // <-- full AnalyticsProduct with SalesHistory retained
totalMargin += marginContribution;
```

At the end of the `await foreach` loop all `n` products (each carrying its own `SalesHistory` list) are held simultaneously in `groupProducts`. Peak memory is O(n × avg_sales_points) — identical to loading the full product list upfront. The streaming only prevents holding two copies at the same time during the initial fetch; it does not cap the working set.

`groupProducts` is used downstream by `GetGroupDisplayName` and `GetGroupAggregatedMarginData`, both of which iterate over the product objects, so the accumulation is load-bearing for the current design. The claim in the comment is therefore false, not just imprecise.

## Why it matters
- The comments create **false confidence** in the module's memory profile. A developer diagnosing high memory usage on a large catalog would not suspect `CalculateAsync` because the code is labelled as the fix.
- Monitoring or load-test budgets based on the streaming assumption will be wrong.
- Any future optimization work that starts from this file will proceed on an incorrect mental model.

## Suggested fix
The minimum fix is to **correct the comments** so they accurately describe the behaviour: the loop reduces peak memory only during the async fetch pipeline (not the total working set), and the full product list is still held by the time calculation finishes.

A deeper fix (if memory is actually a problem) is to avoid storing full `AnalyticsProduct` objects in `groupProducts`: instead accumulate only the pre-computed `GroupMarginData` per group inline, and derive the display name from the first product seen per key (stored as a single string). That makes the working set O(n_groups) rather than O(n_products).
