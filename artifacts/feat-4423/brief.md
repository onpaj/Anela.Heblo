## Module
Configuration

## Finding
`GetConfigurationHandler.GetVersionFromSources()` calls `Assembly.GetExecutingAssembly()` to read version metadata from the assembly containing the handler (`Anela.Heblo.Application`), not from the deployed API entry-point assembly (`Anela.Heblo.API`).

**File:** `backend/src/Anela.Heblo.Application/Features/Configuration/GetConfigurationHandler.cs:75-84`

```csharp
// Priority 2 fallback
var assembly = Assembly.GetExecutingAssembly();          // returns Anela.Heblo.Application
version = assembly.GetCustomAttribute<AssemblyInformationalVersionAttribute>()?.InformationalVersion;
```

`GetExecutingAssembly()` always returns the assembly whose IL is currently running — here that is `Anela.Heblo.Application`. If `AssemblyInformationalVersion` is ever stamped only on the `Anela.Heblo.API` host project (e.g., by a CI step that patches only the entry-point csproj), the fallback silently returns the Application project's version instead of the real deployed version. The primary path (`APP_VERSION` env var) masks this today, but the fallback chain is silently wrong.

## Why it matters
- **Correctness**: The version reported to the frontend could misrepresent the actual deployed API version in any environment where `APP_VERSION` is not set (local dev, ad-hoc environments).
- **Clean Architecture**: Application layer code should not reach out to infrastructure/runtime reflection to discover deployment metadata — version should be injected (e.g., via `IOptions<>`) so the Application layer does not depend on how the host project packages its binary.
- The existing tests (`Handle_FallsBackToAssemblyVersion_WhenAppVersionIsAbsent`) assert only that the version is non-empty and not the default string — they pass against the Application assembly version and do not catch the mismatch.

## Suggested fix
Replace `GetExecutingAssembly()` with `GetEntryAssembly()` (returns the executable host assembly, i.e., `Anela.Heblo.API`) with a null-safe fallback:

```csharp
var assembly = Assembly.GetEntryAssembly() ?? Assembly.GetExecutingAssembly();
```

This is a one-line change. If a stricter fix is preferred, inject the version value via `IOptions<ApplicationVersionOptions>` populated in the API composition root, removing the reflection lookup from the Application layer entirely (also addresses the `IConfiguration` injection noted in #4374).
