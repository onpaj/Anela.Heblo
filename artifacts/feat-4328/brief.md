## Finding
`frontend/src/api/hooks/useDataQuality.ts`, lines 59–74.

The `useDqtRunDetail` hook accepts `resultPage` and `resultPageSize` parameters:
```typescript
export const useDqtRunDetail = (
  runId: string | null,
  resultPage: number = 1,        // ← parameter
  resultPageSize: number = 50,   // ← parameter
) => {
  return useQuery({
    queryKey: dataQualityKeys.runDetail(runId ?? ''),  // ← only runId in key!
    queryFn: (): Promise<GetDqtRunDetailResponse> => {
      const apiClient = getAuthenticatedApiClient();
      return apiClient.dataQuality_GetRunDetail(runId!, resultPage, resultPageSize);
    },
    ...
  });
};
```

The `queryKey` only includes `runId`. The `resultPage` and `resultPageSize` parameters are passed to the API call but not included in the cache key. React Query uses the key to determine cache hits — if a caller changes `resultPage` from 1 to 2, the key is unchanged, so React Query returns the cached page-1 response and never fires a new request.

`GetDqtRunDetailResponse` includes a `TotalDriftResults` field, confirming that pagination was designed to be used. The server-side handler also accepts and applies `ResultPage`/`ResultPageSize` (see `GetDqtRunDetailHandler.cs` line 27 and `GetDqtRunDetailRequest`). The bug is that the hook's cache key doesn't track the pagination state.

## Why it matters
Changing pages on a run detail view will silently serve stale data — the API call is not made, the UI doesn't update. This is a correctness bug that will be invisible until someone tries to implement pagination in the UI.

## Suggested fix
Add pagination parameters to the query key factory and to the `useDqtRunDetail` key:
```typescript
runDetail: (runId: string, resultPage: number, resultPageSize: number) =>
  [...QUERY_KEYS.dataQuality, 'runs', runId, 'detail', resultPage, resultPageSize] as const,
```
And update the `useQuery` call:
```typescript
queryKey: dataQualityKeys.runDetail(runId ?? '', resultPage, resultPageSize),
```
