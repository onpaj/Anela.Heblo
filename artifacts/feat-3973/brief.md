`RunDqtHandler` in `backend/src/Anela.Heblo.Application/Features/DataQuality/UseCases/RunDqt/RunDqtHandler.cs` (lines 46–54) starts the job via fire-and-forget with `Task.Run`. Inside the lambda there is an exception path that is not caught by any handler:

```csharp
_ = Task.Run(async () =>
{
    using var scope = _scopeFactory.CreateScope();
    var runner = scope.ServiceProvider
        .GetServices()
        .SingleOrDefault(r => r.CanHandle(request.TestType))
        ?? throw new InvalidOperationException(   // <- not wrapped in try/catch
              $"No IDqtJobRunner registered for {request.TestType}");
    await runner.RunAsync(run.Id);   // <- RunAsync has its own try/catch, but the line above does not
}, CancellationToken.None);
```

`IDqtJobRunner.RunAsync` implementations (`DriftDqtJobRunner`, `InvoiceDqtJobRunner`) both have an internal `try/catch` that calls `run.Fail()` on exceptions — but the `InvalidOperationException` thrown by the `?? throw` happens **before** `RunAsync` is entered. It is thrown inside the `Task.Run` lambda and the discarded task means it is silently swallowed. The `DqtRun` entity is left permanently in `Running` state with no error recorded.

## Why it matters
If a new `DqtTestType` enum value is added and an API call is made for it before a corresponding `IDqtJobRunner` is registered, `POST /api/data-quality/runs` returns `200 OK` with a run ID, but the run appears stuck forever in the UI with no diagnosis. There is no log entry and no error on the run record.

## Suggested fix
Validate that a runner exists for `request.TestType` **before** persisting the run entity, so invalid test types are rejected synchronously (before any database write and before the fire-and-forget begins). Alternatively, wrap the entire `Task.Run` body in a `try/catch` that calls `run.Fail()` and `_repository.SaveChangesAsync()` for exceptions that occur before `RunAsync` is reached.
