### Question 1
Should the tracking-state-revert capability be added as a new method on `IIssuedInvoiceRepository` (narrow, invoice-specific) or on the shared generic `IRepository<TEntity, TKey>`/`BaseRepository<TEntity, TKey>` (reusable for other importers with the same scoped-repository-plus-batch-loop pattern)? Assumption for planning purposes: start narrow on `IIssuedInvoiceRepository` since no other importer in the codebase was identified as having this pattern during this investigation; promote to the generic base later if a second consumer appears.

**Answer:** Add it as a narrow method on `IIssuedInvoiceRepository` only (e.g. `Task RevertTrackedChangesAsync(IssuedInvoice entity, CancellationToken cancellationToken = default)`). Do not touch `IRepository<TEntity, TKey>` or `BaseRepository<TEntity, TKey>` in this change.

**Rationale:** A repo-wide scan confirms `IssuedInvoiceRepository.GetByIdAsync` is the only custom `GetByIdAsync`/list override across the codebase that omits `.AsNoTracking()` (every other repository — `PurchaseOrderRepository`, `BankStatementImportRepository`, `LeafletDocumentRepository`, `ArticleRepository`, `PackageRepository`, `SmartsuppRepository`, etc. — uses `.AsNoTracking()` for reads), and `MarketingInvoiceImportService` (the codebase's other batch importer) uses `ExistsAsync` + always-`AddAsync`, never a tracked `GetByIdAsync`-then-mutate flow. There is exactly one consumer today; adding to the generic base would be speculative and would leak an invoice-specific EF-state-recovery concern into every other repository's contract.

### Question 2
Is `EntityState.Unchanged` reset sufficient (in-memory only, cheap), or does correctness require `ReloadAsync()` (an extra `SELECT`) to guard against cases where original property values aren't reliably restorable by a plain state flip (e.g., if EF's original-values snapshot was itself altered)? Assumption: `EntityState.Unchanged` reset is sufficient because EF Core retains original values for change-tracked entities separately from current values, and flipping state back to `Unchanged` is EF's standard idiom for discarding in-memory edits without a DB round-trip; this should be validated with a unit test asserting the original values are what's persisted, not the mutated ones.

**Answer:** Use the `EntityState.Unchanged` reset (`context.Entry(invoice).State = EntityState.Unchanged`), not `ReloadAsync()`.

**Rationale:** The only mutation applied before the outer catch in `ExecuteImportInvoice` is `_mapper.Map(invoiceDetail, invoice)` on scalar properties (line 90) — `IssuedInvoice.SyncHistory` (`backend/src/Anela.Heblo.Domain/Features/Invoices/IssuedInvoice.cs:50`) is only populated by `SyncSucceeded`/`SyncFailed`, which run after the transformation pipeline and are excluded from this leak per the answer to Question 4, and `GetByIdAsync` doesn't `Include` `SyncHistory` anyway so no child-collection tracking is in play; there's no evidence any original-values snapshot is altered before the mutation. NFR-1 already states a preference for the in-memory approach, and the codebase has no other place using `ReloadAsync()` as an idiom, so the flag-flip keeps this change minimal and consistent with EF's standard discard-edits pattern.

### Question 3
Does the new-invoice (`isNew == true`) failure path leak in the same way, given that `GetOrCreateAsync` already commits the new row via its own `SaveChangesAsync` before transformations run? If so, should this spec's fix be extended to cover it, or should that be filed as yet another separate issue? Assumption: filed separately, consistent with the brief's explicit framing of this issue as scoped to "existing (re-imported)" invoices only — flag during implementation if investigation shows the new-invoice case is trivially covered by the same code change.

**Answer:** Confirmed: keep it filed separately and out of scope for this spec. Do not extend FR-2's revert logic to `isNew == true`.

**Rationale:** Tracing `ExecuteImportInvoice` (`InvoiceImportService.cs:81-125`): for a new invoice, `GetOrCreateAsync` commits the row via `_mapper.Map<IssuedInvoiceDetail, IssuedInvoice>(invoiceDetail)` + `AddAsync` + `SaveChangesAsync` (lines 132-134), after which EF transitions the entity from `Added` to `Unchanged`; the subsequent `_mapper.Map(invoiceDetail, invoice)` (line 90) then re-applies the *same* `invoiceDetail` values onto the *same* entity instance via the same mapping profile, so it is an idempotent no-op refresh, not a data-changing mutation — unlike the re-import case, where the pre-existing tracked row already held different (previously-synced) values that the mapper genuinely overwrites. So while the entity does technically flip to `Modified` and could leak into a later `SaveChangesAsync` in the same batch, the persisted values are indistinguishable from the values that were already legitimately committed for that new row — there is no silent-corruption risk, only a structurally similar but practically harmless flush. Extending the fix here would require touching the `isNew == true` branch's semantics (which #3566 explicitly required to leave unchanged) for no data-integrity benefit, so it should remain a separate, lower-priority follow-up if pursued at all.

### Question 4
Should the revert also apply if the failure happens inside the *inner* try/catch around `_issuedInvoiceClient.SaveAsync` (lines 99-113), which already catches its own exception and calls `invoice.SyncFailed(...)` — meaning that path does not currently reach the outer catch at all for that specific failure, but does still call `UpdateAsync`/`SaveChangesAsync` immediately after (line 115-116) so does not currently exhibit the leak? Assumption: no revert needed there since that path proceeds to its own `SaveChangesAsync` immediately, which is a legitimate, intentional persist of the "sync failed" status — this spec's revert applies only when an exception escapes to the outer catch (line 120) without reaching the final `SaveChangesAsync`.

**Answer:** Confirmed: no revert for the inner try/catch path. The revert logic in FR-2 applies only when an exception escapes to the outer catch (line 120) without reaching the final `UpdateAsync`/`SaveChangesAsync` (lines 115-116).

**Rationale:** The inner catch's own control flow already falls through to `UpdateAsync`/`SaveChangesAsync` in the same call, so `invoice.SyncFailed(...)` and the line-90 mapping are intentionally and immediately persisted as the correct outcome (a recorded sync failure) — there is no abandoned mutation to revert, and reverting here would incorrectly discard a legitimate status update that the current (pre-#3575) behavior already relies on.
