# Code Review: add-paged-sort-and-paging-tests

## Summary
The implementation appends exactly the six specified test methods to the existing sibling file, in the right location, with no duplicated helpers or structural changes — mechanically it follows the task spec precisely. However, one of the new tests (`GetDocumentsPagedAsync_SortByStatus_BothDirections`) encodes an assumption from the task context that does not hold against the actual persistence mapping: `LeafletDocumentConfiguration` converts `Status` to a lowercase string column via `HasConversion`, so EF Core translates `OrderBy(d => d.Status)` into `ORDER BY "Status"` on the stored string, not the enum ordinal. I verified this concretely with a minimal EF Core/Sqlite reproduction of the exact same conversion, which produced ascending order `Failed, Indexed, Processing` (alphabetical) — the reverse of what the test asserts (`Processing, Indexed, Failed`). This test will fail when actually executed against Postgres.

## Review Result: REVISION_NEEDED

### task: add-paged-sort-and-paging-tests
**Status:** REVISION_NEEDED
**Issues:**
- `GetDocumentsPagedAsync_SortByStatus_BothDirections` (in `backend/test/Anela.Heblo.Tests/Features/Leaflet/Integration/LeafletDocumentRepositoryPagedTests.cs`) asserts ascending order `Processing, Indexed, Failed` and descending order `Failed, Indexed, Processing`, based on the task context's claim that "sorting by Status sorts by this [enum] ordinal." That claim is false for this codebase: `LeafletDocumentConfiguration.cs` (lines 22-27) configures `Status` with `.HasConversion(v => v.ToString().ToLowerInvariant(), v => Enum.Parse<LeafletDocumentStatus>(v, true))`, storing it as a `varchar(16)` column containing `"processing"`/`"indexed"`/`"failed"`. EF Core's LINQ-to-SQL translation orders by the stored provider value, not the CLR enum ordinal, so `ORDER BY "Status"` sorts alphabetically. I confirmed this empirically with a standalone EF Core + Sqlite repro using the identical `HasConversion` call: ascending produced `Failed, Indexed, Processing` and descending produced `Processing, Indexed, Failed` — the exact opposite of what this test asserts. This test will fail on a real run against Postgres (same string-collation behavior applies). The fix is to correct the expected order in both the ascending and descending assertions to match alphabetical order of the stored string values (`Failed, Indexed, Processing` ascending; `Processing, Indexed, Failed` descending), or equivalently document/assert against the actual (string-based) sort semantics rather than the ordinal.
