InvoiceClassification

## Finding
`AmountClassificationRule.Evaluate` calls `decimal.TryParse` without `CultureInfo.InvariantCulture`, so parsing is culture-dependent:

`backend/src/Anela.Heblo.Domain/Features/InvoiceClassification/Rules/AmountClassificationRule.cs:17`
```csharp
return decimal.TryParse(pattern.Substring(2), out var minValue) && invoice.TotalAmount >= minValue;
```

The same pattern occurs on lines 22, 27, 32, and 37.

## Why it matters
On a server configured with Czech locale (decimal separator is comma), a pattern stored as `>=1000.50` (dot separator) will fail to parse and silently return `false` — meaning the rule never matches, with no error or warning. Rules created on one environment (e.g., staging with invariant culture) may silently stop working on another. Because the classification job runs silently and mis-matched invoices are only flagged for manual review, this failure mode is invisible without direct debugging.

## Suggested fix
Use `CultureInfo.InvariantCulture` for all `decimal.TryParse` calls in this rule:

```csharp
return decimal.TryParse(pattern.AsSpan(2), NumberStyles.Number, CultureInfo.InvariantCulture, out var minValue)
       && invoice.TotalAmount >= minValue;
```

Apply consistently to all five parse calls in the method. Also document in the UI that dot is the decimal separator.
