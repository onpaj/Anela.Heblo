## Why it matters
- **Validation at the wrong layer:** application handlers should be able to trust that inputs arriving from the API are within valid ranges. Doing sanitization inside handlers violates the "validate at system boundaries" principle and SRP (a handler's job is to process a valid request, not also to validate it).
- **Silent failure:** the `AllowedPageSizes` allowlist silently returns a different page size than requested, making caller bugs invisible.
- **Self-documenting workaround:** the comment in `ListArticlesHandler` explicitly names the root cause, signalling this is known technical debt.
- **Inconsistent behaviour:** `ListArticlesHandler` clamps to 1–100, while `GetArticleFeedbackListHandler` restricts to `{10, 20, 50}` — callers face different undocumented constraints on different endpoints.

## Suggested fix
1. Add validation attributes to both request types:
   ```csharp
   // ListArticlesRequest
   [Range(1, int.MaxValue)] public int Page { get; set; } = 1;
   [Range(1, 100)] public int PageSize { get; set; } = 20;
   
   // GetArticleFeedbackListRequest — or use FluentValidation
   [Range(1, int.MaxValue)] public int Page { get; set; } = 1;
   [Range(1, 50)] public int PageSize { get; set; } = 20;
   ```
2. Change the controller actions to bind the request type directly: `([FromQuery] ListArticlesRequest request, …)` so model validation fires automatically.
3. Remove the clamping/allowlist code from both handlers along with the workaround comment.
