## Why it matters
The Adapters layer should define its own data models for external sources and map them to Application contracts — not reuse Application contracts as deserialization targets. Two concrete risks:

1. **Tight coupling**: If `BaseResponse` gains a required field, or if `OrgChartResponse` evolves (e.g. the `Organization` property is renamed), the external data source must be updated simultaneously — an invisible coupling between the external data format and the internal API contract.
2. **Silent default values**: Fields inherited from `BaseResponse` (`Success`, `ErrorCode`, `Params`) are absent in the external JSON and silently default to constructor values. If `BaseResponse` construction semantics change, the deserialized response could become incorrect without any compile- or test-time signal.

Violates the Clean Architecture rule that the Adapters layer should translate between external formats and Application contracts, not reuse Application types as I/O models.
