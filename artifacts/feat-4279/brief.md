## Finding
`BankStatementImportDto` declares a computed property that references the domain constant `ImportStatus.Success` directly:

```csharp
// backend/src/Anela.Heblo.Application/Features/Bank/Contracts/BankStatementImportDto.cs:15
public string? ErrorType => ImportResult != ImportStatus.Success ? ImportResult : null;
```

A DTO is a pure data container whose job is to transfer state across the API boundary. `ErrorType` instead encodes a domain rule — "what does success look like?" — inside the contract type. This violates the Single Responsibility Principle: the DTO now acts as both a wire format and a domain-to-presentation translator.

Concrete consequences:
- `BankStatementImportDto` imports `Anela.Heblo.Domain.Features.Bank.ImportStatus`, coupling the contract to a domain class.
- The OpenAPI generator emits `errorType` as a read-only property with no setter; any client that tries to round-trip the DTO will silently lose the field.
- If `ImportStatus.Success` is ever renamed or split into multiple success codes, the DTO silently changes its serialisation contract.

## Why it matters
The project rule (from `development_guidelines.md`) is that DTOs in `contracts/` are data-only; business decisions belong in MediatR handlers or mapping profiles. Having domain logic in a DTO makes the contract harder to reason about and creates a hidden coupling that won't surface in OpenAPI documentation (the generated TypeScript client sees `errorType: string | undefined`, not `errorType == null ↔ success`).

Add `ErrorType` back to the DTO as a plain nullable auto-property:
```csharp

```

This keeps the domain decision in the mapping layer (Application) and the DTO as a plain data container.
