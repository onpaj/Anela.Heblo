PackingMaterials

## Finding
`GetConsumptionHistoryHandler.Handle` fetches the full list of packing materials from the database on every call to resolve material names for the current page of records:

```csharp
// GetConsumptionHistoryHandler.cs:48-49
var materialNames = (await _repository.GetAllAsync(cancellationToken))
    .ToDictionary(m => m.Id, m => m.Name);
```

The paginated result set (`pageSize` records, max 100) may reference only a small subset of all materials. `GetAllAsync` loads every packing material row unconditionally, regardless of how many distinct material IDs appear in the current page.

## Why it matters
The query cost is O(total materials) on every paginated request rather than O(distinct materials on page). While the current material count is small, the pattern is incorrect in principle: the handler already knows which material IDs it needs (from the `records` returned by `GetConsumptionHistoryAsync`), but discards that information and fetches everything. It also means a second full table scan happens after the already-paginated query, for every page load.

## Suggested fix
Collect the distinct material IDs from the returned records and query only those:

```csharp
var materialIds = records.Select(r => r.PackingMaterialId).Distinct();
var materialNames = (await _repository.GetMaterialNamesByIdsAsync(materialIds, cancellationToken));
```

Add `Task<IReadOnlyDictionary<int, string>> GetMaterialNamesByIdsAsync(IEnumerable<int> ids, CancellationToken ct)` to `IPackingMaterialRepository` and implement it as a targeted `WHERE Id IN (...)` query. Alternatively, include the material name in the `MaterialConsumptionHistoryRecord` projection via a JOIN in the existing `GetConsumptionHistoryAsync` query, eliminating the second round-trip entirely.
