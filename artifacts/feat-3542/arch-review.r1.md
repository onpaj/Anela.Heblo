# Architecture Review: Fix Transport Box E2E failures (E2E permission gap + broken nav fallback)

## Skip Design: true

No UI/UX design work is required. FR-1 and FR-2 are pure configuration/routing fixes with zero visual surface. FR-3 (`TransportBoxList` error state) reuses the existing error-panel look (icon, red box, retry button) and only repositions where it renders — it does not introduce a new component, layout, or visual pattern. FR-4 only adds assertions to existing specs. Nothing here requires a designer or a new design-system decision.

## Architectural Fit Assessment

This is a textbook "authorization matrix drift" bug, not a UI defect, and the spec's root-cause chain is fully verified against the code:

- `E2ESessionService.CreateSyntheticUserClaims` (`backend/src/Anela.Heblo.API/Infrastructure/Authentication/E2ESessionService.cs:74-91`) grants only `AccessRoles.Base` and `AccessRoles.FinanceFinancialOverviewRead`. Confirmed — no Warehouse/Logistics role is present.
- `TransportBoxController` carries a class-level `[FeatureAuthorize(Feature.Warehouse_Logistics)]` (Read, default) at line 19, and five actions (`state`, `POST` create, `items`, `description`, `open-by-code`) additionally require `[FeatureAuthorize(Feature.Warehouse_Logistics, AccessLevel.Write)]`. Confirmed by reading `TransportBoxController.cs` — this means **Read alone is not sufficient**: any spec that creates a box (`box-creation`), opens/receives a box by code (`box-receive`), or adds items will 403 even after adding Read-only.
- `AccessRoles.For(Feature.Warehouse_Logistics, AccessLevel.Read/Write)` resolve to `"warehouse.logistics.read"` / `"warehouse.logistics.write"` (`AccessRoles.generated.cs:37-38,96-97`). `FeatureAuthorizeAttribute` sets ASP.NET's `Roles` property directly from these strings (`FeatureAuthorizeAttribute.cs:15,33`), so the E2E user must present a `ClaimTypes.Role` claim with exactly this string value — same mechanism already used for `FinanceFinancialOverviewRead`. FR-1 is a drop-in repetition of an existing, working pattern.
- Frontend gating is a second, independent enforcement point, not a consequence of the API 403: `RequireMenuPath.tsx` checks `ACCESS_ROUTES[path].permissions` against `usePermissionsContext().hasPermission(...)` and hard-redirects (`<Navigate to="/" replace/>`) before the page component ever mounts. `AccessMatrix.generated.cs:67-69,91` confirms `/logistics/transport-boxes`, `/logistics/receive-boxes`, and `#terminal` all require `Warehouse_Logistics` Read. So even a valid API token with only Write (no Read) would still bounce at the router. **Both Read and Write are needed, and Read is the one that unlocks navigation.**
- Permissions reach the frontend via `GET /api/auth/me` → `PermissionsContext` → `usePermissionsContext().permissions` (verified: `AuthController.cs`, `PermissionsContext.tsx`). This is populated from the same role claims set at sign-in, so fixing the backend claim list is sufficient — no separate frontend-side E2E permission stub exists or is needed.
- The generated-file dependency flagged in the spec is resolved: `AccessRoles.generated.cs`, `AccessMatrix.generated.cs`, and `frontend/src/auth/accessMatrix.generated.ts` are all generated by `Anela.Heblo.AccessMatrixGen` from a single hand-edited source of truth, **`access-matrix.json`** at the repo root (confirmed via `AccessMatrixManifest.cs`'s doc comment and the tool's presence at `backend/tools/Anela.Heblo.AccessMatrixGen`). Critically, **`E2ESessionService.CreateSyntheticUserClaims` is a plain hand-written source file, not generated** — FR-1 only needs to reference the existing generated `AccessRoles` constants (as it already does for Finance), and touches zero generated files or the JSON manifest. This removes the dependency risk the spec flagged as open.
- FR-2's fallback URL bug and FR-3's error-swallows-chrome gap are both confirmed exactly as described by reading `e2e-auth-helper.ts:314` and `TransportBoxList.tsx:269-291`.

Net: the spec's diagnosis is correct and complete. The fix is three small, independent, low-risk changes touching three different layers (auth claims, test helper, one component's error branch) — no new components, no schema changes, no new endpoints.

### Key Design Decisions

#### Decision 1: Grant both Read and Write, not Read-only
**Options considered:**
(a) Grant only `WarehouseLogisticsRead` (matches the spec's literal FR-1 wording, which hedges with "and Write, if any test performs a write action").
(b) Grant both `WarehouseLogisticsRead` and `WarehouseLogisticsWrite`.

**Chosen approach:** (b) — grant both, unconditionally, as part of this fix.

**Rationale:** This isn't optional/discretionary — it's forced by what the specs actually do. `box-creation.spec.ts` clicks "Otevřít nový box" (→ `POST /api/transport-boxes`, `[Write]`), and `box-receive.spec.ts` opens/receives a box by code (→ `POST /api/transport-boxes/open-by-code`, `[Write]`, and likely `PUT .../state`, also `[Write]`). Granting Read-only would fix navigation (frontend gate) but leave every write-triggering E2E interaction 403ing — reproducing a subset of the same failures with a more confusing signature (page renders, then the create/receive action silently fails). Grant both roles now; don't defer to "if any test performs a write action" as a follow-up decision, because the affected specs already need it today.

#### Decision 2: Fix E2ESessionService directly, not via `access-matrix.json` + regeneration
**Options considered:**
(a) Add a new `SeedGroupEntry`/role mapping in `access-matrix.json` and regenerate.
(b) Add two `new Claim(ClaimTypes.Role, AccessRoles.WarehouseLogisticsRead/Write)` lines directly to `E2ESessionService.CreateSyntheticUserClaims`, exactly mirroring the existing Finance line.

**Chosen approach:** (b).

**Rationale:** `access-matrix.json` is the source of truth for the **feature catalog and menu-path requirements** (what permissions exist, what a route needs) — it is not a registry of "which synthetic/test identities hold which roles." The E2E user's claim set is application code, already hand-maintained in `E2ESessionService.cs` with a precedent comment explaining the exact same class of fix for Finance. Editing generated files by hand would be overwritten on next codegen run and is explicitly called out as forbidden by the "AUTO-GENERATED... Do not edit by hand" header — routing this through the JSON manifest would be over-engineering for what is a one-service, two-line change, and would incorrectly conflate "what a role grants" with "who has it in this synthetic identity."

#### Decision 3: Scope of FR-3's hardening — wrap, don't restructure
**Options considered:**
(a) Refactor `TransportBoxList` to hoist the header (`<h1>` + action bar) into a layout wrapper that always renders, with `isLoading`/`error`/success as swapped children underneath (bigger diff, touches the collapsible-controls region too).
(b) Keep the component's existing three-way `isLoading` / `error` / success structure, but change only the `error` branch so it renders inside the same outer header + action-bar shell the success path already uses, replacing just the table/summary region with the error message.

**Chosen approach:** (b).

**Rationale:** CLAUDE.md's "surgical changes" rule applies directly — the task is "page chrome must survive API failures," not "redesign the page." Minimal diff: extract the existing `<h1>` block and the "Otevřít nový box"/"Obnovit" button pair so both the error path and the success path render them (e.g., move the header + primary action button above the `if (error)` check, and reduce the error branch to replacing only the results-table region), rather than restructuring collapsible filters, summary cards, etc. Keep "Zkusit znovu" exactly where it is today, just nested inside the persistent shell instead of a standalone card.

## Implementation Guidance

### Directory / Module Structure

No new files/modules for FR-1–FR-3; this is an in-place fix across existing files:

- `backend/src/Anela.Heblo.API/Infrastructure/Authentication/E2ESessionService.cs` — add two claims.
- `backend/test/Anela.Heblo.Tests/Authorization/` — add **one new file**, e.g. `E2ESessionServiceTests.cs` (no existing test file covers this service; every other file in this directory targets a different handler/attribute). Assert `CreateSyntheticUserClaims(...)` returns claims containing `AccessRoles.WarehouseLogisticsRead` and `AccessRoles.WarehouseLogisticsWrite` in addition to the existing two.
- `frontend/test/e2e/helpers/e2e-auth-helper.ts` — change line 314's URL only.
- `frontend/src/components/pages/TransportBoxList.tsx` — restructure the `error`/return-early block (lines 269-291) plus the header block (lines 298-303) and action buttons (lines 480-497) so header+buttons render regardless of `error`.
- `frontend/src/components/pages/__tests__/TransportBoxList.test.tsx` — add one test case for the error path per FR-3's acceptance criteria.
- `frontend/test/e2e/transport/box-items.spec.ts`, `box-workflow.spec.ts`, `ean-integration.spec.ts` — FR-4, one added strict assertion each, in the same file/module per the existing E2E module-guide convention (`docs/testing/e2e-module-guide.md`).

### Interfaces and Contracts

No public interface changes. Two points developers must not deviate from:

1. `E2ESessionService.CreateSyntheticUserClaims` must continue returning a flat `Claim[]` — do not introduce a role-list constant or config-driven role set for this; follow the existing inline-list pattern (see Decision 2). Add:
   ```csharp
   new Claim(ClaimTypes.Role, AccessRoles.WarehouseLogisticsRead),
   new Claim(ClaimTypes.Role, AccessRoles.WarehouseLogisticsWrite),
   ```
   with a comment analogous to the existing Finance one, naming the specific specs that need it (box-creation, box-receive) so the next permission gap is easier to trace.

2. `TransportBoxList`'s error branch must preserve the exact test IDs/text the existing and new tests assert on: `<h1>` text "Transportní boxy", button text matching `/Otevřít nový box/`, and the "Zkusit znovu" retry button must remain wired to the same `refetch()` call. Do not rename these strings — `box-creation.spec.ts` / `boxes-basic.spec.ts` / `box-management.spec.ts` and the component tests all locate elements by this exact text.

### Data Flow

**Before (broken):** E2E login → claims = {Base, FinanceRead} → GET /api/auth/me → permissions = [...,"finance.financial_overview.read"] (no warehouse.*) → RequireMenuPath sees route requires "warehouse.logistics.read" → not present → `<Navigate to="/"/>` → Dashboard renders → spec's `h1`/button/`main` locators for Transport Box pages never match → timeout.

**After (FR-1 applied):** E2E login → claims = {Base, FinanceRead, WarehouseLogisticsRead, WarehouseLogisticsWrite} → GET /api/auth/me → permissions includes both warehouse strings → RequireMenuPath passes → `TransportBoxList`/`TransportBoxReceivePage` mount → `GET /api/transport-boxes` now passes `[FeatureAuthorize(Warehouse_Logistics)]` (Read) → 200 → page renders `h1` + "Otevřít nový box" → write actions (create/open-by-code/state) now pass the Write-level check too.

**FR-2 data flow:** `navigateToTransportBoxReceive`'s UI-nav path is unaffected; only the `catch`/fallback path's `page.goto(...)` target changes from a route with **zero** matching `<Route>` (renders nothing — no `Layout`, no `<main>`) to `/logistics/receive-boxes`, which now (post FR-1) resolves through `guard(...)` to `TransportBoxReceivePage` and renders full page chrome.

**FR-3 data flow:** independent safety net — even after FR-1/FR-2, any future transient 403/500/timeout on `GET /api/transport-boxes` must not blank the header/action bar; `isLoading` / `error` / success all share one persistent header+action-bar region, with only the content region (table/summary/error-message) swapped underneath.

## Specification Amendments

1. **FR-1 should not hedge on Write.** Change "and Write, if any test performs a write action" to an unconditional requirement: grant both `WarehouseLogisticsRead` and `WarehouseLogisticsWrite`. Verified via `TransportBoxController.cs`: `POST /api/transport-boxes` (create), `POST .../open-by-code` (receive), `PUT .../state`, `POST .../items`, `PUT .../description` all require the Write role, and `box-creation.spec.ts`/`box-receive.spec.ts` exercise these. This is not a judgment call to leave to the implementer — it's already determined by the affected specs' behavior.
2. **FR-1's "Dependencies" open item is resolved, not just "worth confirming."** The source of truth is `access-matrix.json` at the repo root, consumed by `Anela.Heblo.AccessMatrixGen` to produce `AccessRoles.generated.cs`, `AccessMatrix.generated.cs`, and `frontend/src/auth/accessMatrix.generated.ts`. However, this fix does **not** touch any of those three files or the JSON manifest — `E2ESessionService.CreateSyntheticUserClaims` is hand-written source that references the generated `AccessRoles` constants, exactly as it already does for `FinanceFinancialOverviewRead`. State this plainly in the implementation PR so no one attempts to route the fix through codegen.
3. **FR-1's test location:** add a new file `backend/test/Anela.Heblo.Tests/Authorization/E2ESessionServiceTests.cs` — there is currently no test file for `E2ESessionService` in that directory (confirmed by directory listing), so "add or update a test" (spec line 41) means *add*, not *update*.
4. **FR-3's acceptance criteria should name the specific lines to change** for implementer clarity: the header (`TransportBoxList.tsx:298-303`) and the action buttons (`TransportBoxList.tsx:480-497`, specifically the "Otevřít nový box" button) must be hoisted so they render outside/above the `if (error)` early return, not just that the error branch gains new JSX copy-pasted from the success path.

## Prerequisites

- No infrastructure, migration, or config changes needed. This is a same-PR, same-deploy fix across backend claims, one E2E helper URL, and one component's render branch.
- No feature flag involved (per `docs/development/feature-flags.md` scope — this is an authorization-claims fix, not a feature rollout).
- Verification requires an actual staging deploy: NFR-1 mandates re-running the full `transport/` E2E suite against `https://heblo.stg.anela.cz` after FR-1+FR-2 land, since the E2E service-principal identity only exists in Staging/Development (`E2ETestController.cs:68-73`) — this cannot be verified against a local/mocked environment.
