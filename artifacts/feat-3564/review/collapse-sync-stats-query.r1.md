## Overall Notes
- **Verified via `git show a63223c`:** the diff matches the implementation summary's description. `GetSyncStatsAsync` now issues one `FirstOrDefaultAsync` against a `GroupBy(x => 1).Select(...)` projection instead of five sequential `CountAsync`/`MaxAsync` calls, satisfying FR-1 and NFR-1's "one round trip, expressed as one `await`" requirement (the InMemory-provider round-trip count itself is out of scope for this task, per spec/arch-review — that's `add-sync-stats-sql-shape-test`).
- **Deviation 1 (non-blocking):** the task-context's code sample computes `LastSyncTime` as `g.Where(x => x.LastSyncTime.HasValue).Max(x => (DateTime?)x.LastSyncTime)`; the actual implementation drops the `Where` filter and uses `g.Max(x => (DateTime?)x.LastSyncTime)` directly. This is functionally equivalent: both `Enumerable.Max`/`Queryable.Max` over a nullable value-type selector and SQL's `MAX()` aggregate ignore `NULL`/`null` inputs and return `null` only if every value is null (or the sequence is empty) — they do not throw. The new `GetSyncStatsAsync_WithNoInvoiceHavingLastSyncTime_ReturnsNullLastSyncTime` test (all invoices null `LastSyncTime`) exercises exactly this path and is claimed passing, which corroborates the equivalence. Not a correctness issue; the spec's stated rationale for keeping the `Where` ("so rows without a sync time... don't throw") does not actually apply to nullable `Max`.
- **Deviation 2 (non-blocking):** empty/zero-match handling is implemented as an explicit `if (stats == null) { return new IssuedInvoiceSyncStats { ...all zero/null... }; }` block rather than the task-context's inline `stats?.Total ?? 0` null-coalescing style. Equivalent outcome (all counts `0`, `LastSyncTime = null`, no `NullReferenceException`), just more verbose — a style choice, not a defect.
- **Test-coverage observation (informational, not blocking):** FR-1's acceptance criteria in `spec.r1.md` call out the zero-matching-invoices case explicitly ("no `NullReferenceException`... `TotalInvoices=0`... `LastSyncTime=null`"), but neither this task's task-context (Step 1) nor the added tests include a case with *zero* invoices in the date range (as opposed to invoices present but none synced). The task-context itself didn't ask for that specific test, so this isn't a task-context compliance gap, but it is a residual spec-level gap worth flagging — likely worth a follow-up fact (e.g. `GetSyncStatsAsync_WithNoInvoicesInRange_ReturnsAllZeroStats`) either here or in the `add-sync-stats-sql-shape-test` task. The code path itself was manually verified correct by inspection (the `if (stats == null)` branch returns a fully zeroed/null DTO).
- **Architecture adherence:** confirmed against `arch-review.r1.md` — change is confined to `IssuedInvoiceRepository` in `Anela.Heblo.Persistence`, no changes to `IIssuedInvoiceRepository`, `IssuedInvoiceSyncStats`, or any caller (`GetIssuedInvoiceSyncStatsHandler`, `InvoicesController`), consistent with "surgical change" guidance.
- **Build:** independently rebuilt `backend/src/Anela.Heblo.Persistence/Anela.Heblo.Persistence.csproj` — succeeds with 0 warnings/0 errors.
