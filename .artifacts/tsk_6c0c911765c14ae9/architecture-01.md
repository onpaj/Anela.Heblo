## Correction required — §2's worst-case latency arithmetic undercounts by one retry cycle

Design §2 computes worst case as `(MaxRetryAttempts + 1) × TotalTimeBudget` = `4 × 10s + ~1.4s ≈ 41s`, and after the proposed reduction, `4 × 3s + ~1.4s ≈ 13.4s`. Re-derive this from the actual retry loop shape (`MaxRetryAttempts=3` in `DbResilienceOptions.cs:7`, exponential backoff `BaseDelay=200ms` → `MaxRetryDelay=4s`, `UseJitter=true`, applied *between* attempts, in `DbResiliencePipelineProviderTests.cs`'s own pattern and Polly's `RetryStrategyOptions` semantics): 4 total attempts (1 initial + 3 retries), each individually bounded by `TotalTimeBudget`, with 3 backoff delays *between* the 4 attempts (not before the first). The delay sequence for exponential backoff with `BaseDelay=200ms` is approximately `200ms, 400ms, 800ms` before jitter (capped at `MaxRetryDelay=4s`, never reached at these attempt counts) — summing to ~1.4s, which the design's number already reflects. So the arithmetic itself (`4 × budget + ~1.4s`) is actually right; what's inconsistent is that §2's own explanatory text says "roughly 4 × 10s" for the **before** case, but the *retry is not even enabled* for `TimeoutRejectedException` today — today's actual worst case for a wedged call is one `TotalTimeBudget` (10s), full stop, because the exception isn't retried. The "41s today" framing compares a hypothetical not-yet-existing behavior against itself, which could mislead whoever writes the PR description into thinking this fix *reduces* latency (10s→13.4s is an increase, not a decrease, and must be described as such). **Correct the design text to state plainly: today a fully-wedged call fails in ~10s (single attempt, no retry); after this fix it can take up to ~13.4s (4 attempts) before giving up — an explicit latency-for-availability tradeoff, worse in the worst case, better in the common case where a retry succeeds within a few seconds.** This doesn't change the recommended `TotalTimeBudget: 10s→3s` value or the plan of record — it's a correction to the justification text so the PR description and the eventual reviewer don't misread the direction of the tradeoff.

## Addition required — the interceptor's `OpenStopwatch` AsyncLocal needs an explicit reset-on-failure test, because §5's fix introduces a real (if narrow) leak-shape risk

Design §5's fix stops and clears `OpenStopwatch` in the failure path exactly as `RecordOpenLatency` does on success — correct and necessary. But `AsyncLocal<Stopwatch?>` is per-logical-call-context; if a connection-open attempt is abandoned in a way that skips *both* `ConnectionOpened(Async)` and `ConnectenFailed(Async)` (e.g. the ambient token cancels the open between `ConnectionOpening` setting the stopwatch and Npgsql raising either event — plausible for exactly the `TaskCanceledException@NpgsqlWriteBuffer.Flush` pattern this whole task is about, since a write-buffer flush during the connection handshake could throw past EF's interceptor pipeline entirely), the stopwatch is never cleared for that async-local flow. This is not a functional bug (the value is scoped to that async chain and gets GC'd when the chain ends; a pooled connection's next open call re-enters `ConnectionOpening` and overwrites it), but it means the design's confidence that "every failure now feeds the metric" is not 100% — there's a third path (neither opened nor `ConnectionFailed` fires) that still produces zero signal, and it may be common for exactly the write-buffer-flush cancellations under investigation. Before implementation:
- Add a unit test against `NpgsqlConnectionInterceptor` (no test file exists for it today — confirmed via file search) asserting `RecordPoolExhaustionWait` fires when `ConnectionFailed`/`ConnectionFailedAsync` is invoked after `ConnectionOpening`, with elapsed time above threshold.
- Explicitly note (in the design or as a comment) that a connection-open cancelled by the ambient token *before* Npgsql raises either `ConnectionOpened` or `ConnectionFailed` remains invisible to this metric — this is a known residual gap, not a regression introduced by this change, and closing it would require hooking a lower-level Npgsql/ADO.NET event this interceptor doesn't have access to. Flagging it now prevents FR-3/FR-4's confirm/refute gate from being read as more complete than it is — if `withPoolWait` in §6's KQL comes back low, that could mean "no pool contention" or it could mean "pool contention that manifested through this exact silent third path," and the difference matters for whether FR-4 gets skipped.
