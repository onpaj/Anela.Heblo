# Architecture assessment: MCP tools bypass the per-feature authorization gate

## Verdict

**Approved as designed.** I re-read every file the design references — `CatalogMcpTools.cs`, `MeetingTasksMcpTools.cs`, `KnowledgeBaseTools.cs`, `LeafletTools.cs`, `ManufactureOrderMcpTools.cs`, `ManufactureBatchMcpTools.cs`, `UserManagementMcpTools.cs`, `McpModule.cs`, `AccessRoles.generated.cs`, `Feature.generated.cs` (via the switch), `FeatureAuthorizeAttribute.cs`, `CurrentUserService.cs`, `CatalogMcpToolsTests.cs`, `MeetingTasksMcpToolsTests.cs`, and every sibling controller's `[FeatureAuthorize]` attribute — and every factual claim the design makes checks out against current source, not against a stale mental model. One scope correction below (LeafletTools doc entry) and a couple of implementation call-outs; no structural objection.

## Alignment with existing patterns

- The two reference implementations (`CatalogMcpTools.GetProductMargins`, `MeetingTasksMcpTools.EnsureReadAccess`) are exactly as the design describes: `AccessRoles.For(Feature.X, AccessLevel.Read)` → `_currentUserService.IsInRole(role)` → `throw new McpException("[FORBIDDEN] You do not have permission to access {name} (requires {role}).")`. Extracting this into `McpAuthorizationExtensions.EnsureFeatureAccess` is a straight Extract Method refactor with zero behavior change to the two existing call sites — low risk.
- Feature/role mapping in the FR-1 table is verified correct against both `AccessRoles.generated.cs`'s `For(Feature, AccessLevel)` switch and each sibling controller's class-level `[FeatureAuthorize]`: `CatalogController` → `Products_Catalog` (`CatalogController.cs:22`), `ManufactureOrderController` → `Manufacture_ManufactureOrders` (`:19`), `ManufactureBatchController` → `Manufacture_BatchPlanning` (`:11`), `KnowledgeBaseController` → `Customer_KnowledgeBase` (`:17`), `LeafletController` → `Marketing_Leaflet` (`:19`), `UserManagementController` → `Admin_Administration` (`:10`). `FeatureAuthorizeAttribute`'s single-feature constructor defaults `AccessLevel.Read` (`FeatureAuthorizeAttribute.cs:11`), confirming "Read" is the correct level for all of these (none of the affected MCP methods are mutating — verified by inspection, they're all `Get*`/`Search*`/`Ask*`/`Calculate*`).
- `Anela.Heblo.API/*Extensions.cs` is an established naming/placement convention in this API project (`ApplicationBuilderExtensions.cs`, `AuthenticationExtensions.cs`, `ServiceCollectionExtensions.cs`, etc.) — `McpAuthorizationExtensions.cs` in `MCP/` fits it exactly. Domain-layer placement was correctly rejected: `McpException` comes from the `ModelContextProtocol` SDK package, which `Anela.Heblo.Domain` does not and should not reference.
- DI: `McpModule.cs` registers each tool class via `.WithTools<T>()` with no explicit factory — confirmed by reading it (`McpModule.cs:17-23`). `CatalogMcpTools` and `MeetingTasksMcpTools` already receive `ICurrentUserService` through this exact mechanism today, in production, over the MCP HTTP transport. Adding the same constructor parameter to the other five classes is proven-safe, not a new integration risk.
- `CurrentUserService.IsInRole` (`Features/Users/CurrentUserService.cs:57-60`) reads `_httpContextAccessor.HttpContext?.User?.IsInRole(role)`, the same `HttpContext.User` populated by `.RequireAuthorization()` on `/mcp` — this is exactly what already backs the two working gated tools, so there's no reason to expect it behaves differently for the newly-gated ones.

## Proposed architecture

Static extension method `McpAuthorizationExtensions.EnsureFeatureAccess(this ICurrentUserService, Feature, string resourceName, AccessLevel level = Read)` in `Anela.Heblo.API/MCP/McpAuthorizationExtensions.cs`, called as the **first statement** of every currently-ungated tool method (18 call sites across 6 classes), plus migration of the 2 existing hand-rolled checks onto it (4 call sites in `MeetingTasksMcpTools`, 1 in `CatalogMcpTools.GetProductMargins`) so there is exactly one implementation of "resolve role → check → throw" in the codebase. This is the right shape: it closes the gap with the minimum structural change, matches the pattern the two correct classes already established, and requires no SDK-level hook, no MVC involvement, and no change to `/mcp`'s `.RequireAuthorization()` mapping.

No viable alternative was left unexamined by the plan: a global SDK filter/interceptor was correctly identified and correctly deferred (open question in plan-01.md) rather than adopted — introducing a new enforcement mechanism (whatever `ModelContextProtocol.AspNetCore` 1.0.0 might expose) inside a fix for a security gap is exactly the kind of scope creep that risks shipping the vulnerability fix late or wrong. Per-method + shared helper is the low-risk, provably-correct choice for this pass; a filter-based refactor is legitimate future cleanup, not a blocker.

## Implementation guidance

**Placement rule — verified, not just asserted.** I read `KnowledgeBaseTools.cs` and `LeafletTools.cs` directly. The design's claim is exactly right:
- `KnowledgeBaseTools.SearchKnowledgeBase` / `AskKnowledgeBase` wrap the body in `try { ... } catch (Exception ex) { throw new McpException($"Failed to ..."); }` with **no** `catch (McpException) { throw; }` guard (`KnowledgeBaseTools.cs:31-44`, `:54-67`). If `EnsureFeatureAccess` were called inside that `try`, its `McpException` would be swallowed by the generic `catch (Exception ex)` and re-wrapped as `"Failed to search knowledge base: [FORBIDDEN] ..."` — losing the `FORBIDDEN` prefix a caller or test might pattern-match on, and burying it under a misleading "Failed to..." wrapper.
- `LeafletTools.GenerateLeaflet` **does** have `catch (McpException) { throw; }` before its generic catch (`LeafletTools.cs:57-60`), so it would survive being placed inside the `try` — but placing the guard before the `try` uniformly in all six classes is still correct: it avoids a class-by-class audit of catch-guard presence and removes any dependency on that detail staying true in the future.

Concretely: guard call is the first line of the method body, before any `try`, in all six classes — no exceptions to this rule.

**DI wiring.** `ManufactureOrderMcpTools`, `ManufactureBatchMcpTools`, `KnowledgeBaseTools`, `LeafletTools`, `UserManagementMcpTools` each need `ICurrentUserService` added to their constructor (field + param). `KnowledgeBaseTools` and `LeafletTools` already take `ILogger<T>`, so this is an additive constructor param on top of what's there, not a new pattern for those two files. No `McpModule.cs` edit needed — `.WithTools<T>()` resolves via the container already.

**Test-fixture nuance — verified against Moq's actual last-matching-setup-wins semantics, not assumed.** `CatalogMcpToolsTests`'s constructor currently sets up nothing (`CatalogMcpToolsTests.cs:27-32`); all 7 non-margin happy-path tests (`GetCatalogList_ShouldMapParametersCorrectly`, etc.) never stub `IsInRole` because today those methods don't check it. Once the guard is added, those tests will call `IsInRole(AccessRoles.ProductsCatalogRead)`, which returns Moq's bare-mock default (`false`) and throws `McpException` unless a constructor-level default stub is added. I confirmed the design's claimed fix works: add `_currentUserServiceMock.Setup(s => s.IsInRole(AccessRoles.ProductsCatalogRead)).Returns(true);` in the constructor; the existing `GetProductMargins_ThrowsMcpException_WhenUserLacksFeature` test's `IsInRole(It.IsAny<string>()) → false` setup is configured later (inside the test method body, which runs after the constructor), and Moq resolves the most-recently-configured matching setup for a given call — so for a call to `IsInRole("products.product_margins.read")`, only the `It.IsAny<string>()` setup matches (the constructor's exact-string setup for `products.catalog.read` doesn't match a different string), and it correctly returns `false`. No collision. Apply the same "constructor stub defaults to allow, test overrides to deny" pattern already used in `MeetingTasksMcpToolsTests.cs:25-33` to the other four newly-touched test fixtures.

## Scope correction to the design (doc, FR-3)

I read `docs/integrations/mcp-server.md` in full. `LeafletTools.GenerateLeaflet` is not just missing its permission note — **it has no section in the doc at all** (`grep -n "Leaflet" docs/integrations/mcp-server.md` returns nothing). The design already flagged this as something to "confirm during implementation," correctly hedged rather than asserting a location that doesn't exist — but implementers should treat it as settled, not open: add a new `**Leaflet (1)**` group (matching the existing group format, e.g. `**User Management (1)**` at line 28) with `GenerateLeaflet` and its required-permission note, rather than trying to append a note to a non-existent existing entry.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| A newly-gated method's happy-path test silently starts throwing `FORBIDDEN` because its fixture never stubs `IsInRole` | Constructor-level default-allow stub per fixture (pattern proven in `MeetingTasksMcpToolsTests`), verified compatible with Moq's setup-resolution order above |
| Guard placed inside a `try`/generic-`catch` gets re-wrapped, hiding `FORBIDDEN` from callers/tests | Guard is always the first statement, before any `try` — verified necessary specifically for `KnowledgeBaseTools`, applied uniformly to avoid a per-class audit |
| Feature/role mismatch between an MCP tool and its sibling controller (over- or under-gating) | Every mapping in FR-1 verified directly against the controller's `[FeatureAuthorize]` attribute in this pass — no divergence found |
| Doc update misses `LeafletTools` because no existing anchor exists | Called out explicitly above — add a new doc group, not an edit to a nonexistent one |

## Prerequisites before implementation begins

None outstanding. `ICurrentUserService`, `AccessRoles`, `Feature`, `AccessLevel`, and `McpException` are all already in use in this exact combination in production code (`CatalogMcpTools.GetProductMargins`, `MeetingTasksMcpTools`); no new package, no schema change, no MVC/routing change, no `McpModule.cs` change. Implementation can proceed directly per plan-01.md's 6-step sequence.
