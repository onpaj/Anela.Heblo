# Plan: KnowledgeBase hooks — replace `(apiClient as any).http.fetch` with generated client calls

## Summary

`frontend/src/api/hooks/useKnowledgeBase.ts` bypasses the generated NSwag client for all 9 KnowledgeBase endpoints (10 hooks), using 18 occurrences of `(apiClient as any).baseUrl` / `(apiClient as any).http.fetch` plus ~10 hand-duplicated DTO interfaces. The fix is to call the generated `knowledgeBase_*` methods directly, delete the duplicated interfaces, and adapt the handful of consumers whose typing assumptions (required vs. optional fields, string dates vs. `Date`) no longer hold once real generated types flow through. One endpoint (`useSubmitFeedbackMutation`) keeps a manual fetch, but via the documented `getApiBaseUrl()` + `getAuthenticatedFetch()` escape hatch instead of `(apiClient as any)`, because its 409-as-success contract isn't expressible through the generated method (which throws on any non-200/204 status).

## Context

This is the KnowledgeBase instance of a recurring finding class already fixed for DataQuality (#3816, this repo's `useDataQuality.ts`), Photobank (#3815), Manufacture (#3797/#3730/#3802), Expedition (#3823), Analytics (#3333), Bank (#3395). `useDataQuality.ts` is the closest prior fix and the template to follow: same violation shape (raw fetch + local DTOs), same category of fallout (generated types make optional what local hand-rolled types declared required, and use `Date` where locals used `string`). This task is pure refactor — no backend change, no intended behavior change — but, as with DataQuality, swapping in the real generated types surfaces genuine type mismatches in consumers that must be reconciled, not glossed over with `as any`.

## Investigation findings (read before implementing)

Compared `useKnowledgeBase.ts:10-142`'s local interfaces against `frontend/src/api/generated/api-client.ts` (methods at lines 5196-5567, DTOs at lines 23938-24877). Findings:

1. **All 9 endpoints already have typed generated methods with matching DTOs**: `knowledgeBase_GetDocuments`, `knowledgeBase_GetDocumentContentTypes`, `knowledgeBase_Search`, `knowledgeBase_GetChunkDetail`, `knowledgeBase_Ask`, `knowledgeBase_DeleteDocument`, `knowledgeBase_GetFeedbackList`, `knowledgeBase_SubmitFeedback`, `knowledgeBase_UploadDocument`. Parameter order/optionality matches the hooks' existing param objects 1:1 — this is a direct swap, not a redesign.
2. **`DocumentSummary`**: generated `createdAt?: Date`, `indexedAt?: Date | undefined` (local: `string`, `string | null`). All other fields (`id`, `filename`, `status`, `contentType`, `firstChunkId`) are optional in the generated class vs. required locally — harmless for JSX children (React renders `undefined` as nothing) but breaks anywhere a value flows into a prop/param typed as required `string` (e.g. `<StatusBadge status={doc.status} />` in `KnowledgeBaseDocumentsTab.tsx:359`).
3. **`KnowledgeBaseDocumentsTab.tsx:363,367`** does `new Date(doc.createdAt).toLocaleDateString('cs-CZ')` / `new Date(doc.indexedAt).toLocaleDateString(...)`. Once `createdAt`/`indexedAt` are already `Date`, wrapping in `new Date(...)` is a type error (TS's `Date` constructor overloads take `string | number`, not `Date`) — must become `doc.createdAt.toLocaleDateString('cs-CZ')` directly (with an optional-chaining/fallback for the now-optional `createdAt`).
4. **`GetChunkDetailResponse.documentType`** is the generated `DocumentType` enum (`KnowledgeBase | Conversation | Leaflet | Article`) instead of the local `'KnowledgeBase' | 'Conversation'` union. `ChunkDetailModal.tsx:65`'s `data.documentType === 'Conversation'` still compiles unchanged (comparing an enum-typed value to one of its own string literals is valid TS). `indexedAt` becomes `Date | undefined`; `ChunkDetailModal.tsx:68` already calls `formatDateTime(data.indexedAt)`, and `formatDateTime`/`formatDate` in `utils/formatters.ts` already accept `string | Date | null | undefined` — **no change needed there**.
5. **`AskQuestionResponse`**: `answer?: string` and `sources?: SourceReference[]` are optional in the generated class (local: both required). `KnowledgeBaseSearchAskTab.tsx:148,150` (`<ReactMarkdown>{ask.data.answer}</ReactMarkdown>`, `<SourceAccordion sources={ask.data.sources} .../>`) and the same pattern in the dead-but-still-compiled `KnowledgeBaseAskTab.tsx` need `ask.data.answer ?? ''` / `ask.data.sources ?? []`. `id?: string | undefined` (local was `string | null`) — the existing `{ask.data.id && <KnowledgeBaseFeedback logId={ask.data.id} />}` guard already narrows correctly, no change needed.
6. **`SearchDocumentsResponse.chunks`** is optional (`ChunkResult[] | undefined`); `KnowledgeBaseSearchTab.tsx:113` does `search.data.chunks.length` / `.map(...)` directly — needs `(search.data.chunks ?? [])`. `ChunkResult` and `SourceReference` themselves are structurally identical to the local interfaces (no `Date` fields) — drop-in.
7. **Two near-duplicate component pairs exist**: `KnowledgeBaseSearchAskTab.tsx` (the one actually wired into `pages/KnowledgeBasePage.tsx`) vs. the unused `KnowledgeBaseAskTab.tsx` + `KnowledgeBaseSearchTab.tsx` (not imported anywhere outside their own tests — dead in the running app, confirmed via grep). Both still get typechecked/tested and both import `SourceReference`/`ChunkResult` from the hook file, so both need the same optional-field fallout fixes in step 5/6 even though only one is live. Do not delete the dead pair — out of scope for this task.
8. **Feedback-list is a special case.** The hook's local `GetFeedbackListResponse.logs`/`.stats` already delegate to `RagFeedbackLogSummary`/`RagFeedbackStats` from the *shared* `frontend/src/components/feedback/ragFeedbackTypes.ts` (string `createdAt`, `string | null` fields) — not hand-duplicated. That shared file is also consumed by the **Smartsupp** draft-reply feedback hook (`components/customer-support/smartsupp/hooks/useSmartsuppDraftReplyFeedbackListQuery.ts`), which independently does its own raw-fetch (separate, not-yet-fixed arch-review target, out of scope here), and by shared display components (`RagFeedbackDetailExtra.tsx`, `useKbFeedbackAdapter.ts`, `KnowledgeBaseFeedbackPage.tsx`) that all assume `createdAt: string`. The generated `GetFeedbackListResponse.logs` is `RagFeedbackLogSummary[]` — a **different, same-named** generated class with `createdAt?: Date` and `expandedQuery?: string | undefined` (vs. local `string | null`). Swapping the hook's return type wholesale to the generated shape would force type changes into `ragFeedbackTypes.ts` and, transitively, into the Smartsupp module — well outside this task's scope. **Decision: call the generated `knowledgeBase_GetFeedbackList` method for the fetch/parse, but map its result back into the existing local `GetFeedbackListResponse`/`FeedbackLogSummary`/`FeedbackStatsDto` shape (`Date` → ISO string via `.toISOString()`, `undefined` → `null` where the local type says `| null`) before returning from `queryFn`.** This still eliminates all `as any`/manual URL building for this endpoint (the actual violation) without touching the shared feedback-type file or any Smartsupp code.
9. **`useSubmitFeedbackMutation`'s 409 handling has no generated equivalent.** `processKnowledgeBase_SubmitFeedback` throws via `throwException(...)` for any status other than 200/204 — it cannot return the `{ alreadySubmitted: true }` sentinel on 409 the way the hook currently does. Per the doc's documented escape hatch and existing codebase precedent (`api/hooks/usePackingDashboard.ts`, `pages/ExpeditionListArchivePage.tsx` both already use `getApiBaseUrl()` + `getAuthenticatedFetch()` for cases the typed client can't express), keep this one hook on manual fetch, replacing `(apiClient as any).baseUrl`/`.http.fetch` with `getApiBaseUrl()` + `getAuthenticatedFetch()`. Type the outgoing payload against the generated `SubmitFeedbackRequest` class instead of the local hand-rolled interface (delete the local one). Note: `getAuthenticatedFetch()` does **not** trigger the global 401-redirect/error-toast handling that `getAuthenticatedApiClient()`'s internal fetch does — this is a real, documented behavior difference from today, but matches the established pattern elsewhere in the codebase (React Query's own `isError` is the fallback signal; no consumer currently renders a submit-feedback error message, and adding one is a UX feature, not part of this refactor).
10. **Upload needs a `FileParameter` wrapper.** `knowledgeBase_UploadDocument(file: FileParameter | null | undefined, documentType: string | null | undefined)` expects `{ data: any; fileName: string }`, not a raw `File`. The mutationFn must build `{ data: file, fileName: file.name }` before calling the generated method (a browser `File` is a valid `Blob`, so `data: file` is fine).
11. **The local `DocumentType` union type (`'KnowledgeBase' | 'Conversation'`)** is not a duplicated response DTO — it's a UI-scoped restriction used only by `KnowledgeBaseUploadTab.tsx` to constrain the upload dropdown to 2 of the generated enum's 4 values (`Leaflet`/`Article` aren't valid upload targets). The generated `knowledgeBase_UploadDocument`'s `documentType` param is a plain `string`, so this local union is compatible and **should be kept as-is** — no generated equivalent to swap to without either losing the 2-value restriction or fighting string-enum literal assignability in the upload state (`useState<Record<string, DocumentType>>`).
12. **The local `ChunkDetail` interface (`useKnowledgeBase.ts:101-110`) is dead** — not used anywhere, including inside the hook file itself (only `GetChunkDetailResponse` is actually used as a return type). Safe to delete outright.
13. **The existing hook unit test (`api/hooks/__tests__/useKnowledgeBase.test.ts`) mocks `getAuthenticatedApiClient()` to return a plain `{ baseUrl, http: { fetch } }` object**, not a real `ApiClient` — it will not have `knowledgeBase_*` methods and must be rewritten. The already-fixed `useDataQuality.ts` has the template: `api/hooks/__tests__/useDataQuality.test.ts` uses `mockAuthenticatedApiClient(mockClient)` + `createQueryClientWrapper()` from `frontend/src/api/testUtils.ts`, mocking `../../client` wholesale and stubbing individual `apiClient.dataQuality_*` methods as `jest.fn()`. Follow the same pattern here, mocking each `knowledgeBase_*` method used.
14. **The existing upload test passes `result.current.mutate(file)`** (a bare `File`, not `{ file, documentType }`) — this doesn't match the hook's current `mutationFn` signature at all and only "works" today because the mocked `http.fetch` never inspects its arguments. This is a pre-existing test bug that must be corrected as part of rewriting the test (call `mutate({ file, documentType: 'KnowledgeBase' })` or similar) rather than carried forward.

  - AC: `grep -c "as any" frontend/src/api/hooks/useKnowledgeBase.ts` returns 0 overall.
  - AC: the local `DocumentType` union and the local `GetFeedbackListResponse`/`FeedbackLogSummary`/`FeedbackStatsDto` aliases (which delegate to `ragFeedbackTypes.ts`, not to a generated-client duplicate) are the only hand-written types remaining, per findings #8 and #11.
- **FR-11**: All 6 consuming components with fallout from optional/`Date`-typed fields are updated: `KnowledgeBaseDocumentsTab.tsx` (finding #2-3), `ChunkDetailModal.tsx` (finding #4, expected to need no change beyond the import source), `KnowledgeBaseSearchAskTab.tsx` + `KnowledgeBaseAskTab.tsx` (finding #5), `KnowledgeBaseSearchTab.tsx` (finding #6).
  - AC: no `Date` object is ever passed to `new Date(...)` a second time; no optional generated field is passed to a prop/param that declares it required without an explicit `?? fallback`.

## Non-functional requirements

- **Type safety**: `npm run build` (tsc) must pass with zero new `as any`/`as unknown as X` introduced to paper over the type changes; prefer `?? fallback` and precise optional typing over assertions, consistent with the DataQuality precedent.
- **No behavior change** except the documented, accepted one in finding #9 (loss of automatic 401-redirect/toast on the feedback-submit path, matching existing codebase precedent for the `getAuthenticatedFetch()` escape hatch). Request URLs, query params, request/response JSON payloads, and cache keys stay identical — verify manually in the browser: Documents tab loads/filters/sorts/paginates and deletes, content-type filter populates, Search tab returns chunks, Ask tab returns an answer + sources + feedback submission (including a forced double-submit to exercise the 409 path), chunk-detail modal opens from both a search result and a document row, upload succeeds for both document types, and the Feedback Browser page loads/paginates.

## Data model

No backend/data model changes. Frontend-only: `DocumentSummary`, `GetDocumentsResponse`, `GetDocumentContentTypesResponse`, `ChunkResult`, `SearchDocumentsRequest`, `SearchDocumentsResponse`, `GetChunkDetailResponse`, `DocumentType` (enum, generated — not used directly, see finding #11), `AskQuestionRequest`, `AskQuestionResponse`, `SourceReference`, `DeleteDocumentResponse`, `GetFeedbackListResponse` (generated, used only internally by the mapping step per FR-8), `SubmitFeedbackRequest`, `SubmitFeedbackResponse` (unused — see FR-9, generated method not called), `UploadDocumentResponse2` (already generated at `frontend/src/api/generated/api-client.ts:23938-24877`, confirmed present) become the source of truth in place of the hand-rolled duplicates, except where finding #8/#11 explicitly keep a local shape for cross-module or UI-scoping reasons.

## Interfaces

No API surface changes — same 9 endpoints (`GET/POST/DELETE /api/KnowledgeBase/...`), called through the typed generated methods (`knowledgeBase_*`) instead of hand-built URLs, except `SubmitFeedback` which keeps a manual `getAuthenticatedFetch()` call to the same `POST /api/KnowledgeBase/feedback` URL for the reason in finding #9.

## Open questions

- **Whether to instantiate the generated request classes (`new SearchDocumentsRequest(...)`, `new AskQuestionRequest(...)`) or pass plain object literals.** Both are structurally valid since `JSON.stringify` only cares about own enumerable properties and the generated `toJSON()` doesn't rename fields. Default: use `new ClassName({...})` for consistency with how `useDataQuality.ts` builds `RunDqtRequest`, unless a sibling KB-adjacent hook shows a plain-object convention instead.
- **Whether `RagFeedbackStatsDto`'s `avgPrecisionScore`/`avgStyleScore` (`number | undefined` generated) need `null` coercion for the FR-8 mapping**, given the local `RagFeedbackStats` interface declares them `number | null`. Default: coerce `undefined → null` for full local-type fidelity, consistent with the rest of the mapping.
- **Confirming finding #7's dead-component claim before touching it.** The plan treats `KnowledgeBaseAskTab.tsx`/`KnowledgeBaseSearchTab.tsx` as unreferenced outside their own tests based on a repo-wide grep; if the implementer's build/lint turns up an import this plan missed, treat that component as live and apply the same fixes with equal care (not as an afterthought).
