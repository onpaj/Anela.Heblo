# Architecture review: Lock down `DiagnosticsController`

## Verdict

**Approved as designed.** Every factual claim in `design-01.md` was checked directly against the current source and holds. The design is internally consistent, follows the one precedented pattern in this codebase for this exact class of endpoint (`E2ETestController`), and does not introduce any new abstraction, role, or auth mechanism. No changes required before implementation proceeds.

## What was verified against the codebase

- **`DiagnosticsController.cs:1-114`** — confirmed no `[Authorize]`, no environment guard, and `GetApplicationInsightsConfig` (lines 91-113) returns `InstrumentationKey` (raw GUID, line 107) and `ConnectionStringSource` (50-char connection-string prefix, line 109) exactly as the plan/design describe. `TelemetryClient` is 2.22.0; `InstrumentationKey` is not obsolete in this SDK version, so no compile warning risk from continuing to read it (only the *exposure* is removed).
- **`AuthenticationExtensions.cs:104-114`** — `DefaultPolicy` is exactly `RequireAuthenticatedUser().RequireRole(AccessRoles.Base)`, no `FallbackPolicy`. Confirms the design's premise: `[Authorize]` with no arguments on the controller is sufficient and is the same mechanism already used elsewhere (`ApplicationBuilderExtensions.cs:137`, `MapMcp(...).RequireAuthorization()`).
- **`ApplicationBuilderExtensions.cs:124`** — `app.MapControllers()` unconditional, no `.RequireAuthorization()` chained. Confirms unattributed controllers stay anonymous today, and that adding `[Authorize]` is the correct, minimal fix (no pipeline-level change needed).
- **`E2ETestController.cs`** — precedent confirmed to be a *per-action* `IWebHostEnvironment` guard (`if (!_environment.IsEnvironment("Staging") && !_environment.IsDevelopment()) return NotFound(...)`), not a class-level or filter-based guard, and it coexists with per-action `[Authorize(AuthenticationSchemes = "E2ETestCookies")]`/`[AllowAnonymous]`. The design's `TryBlockInProduction()` private-helper-per-action shape matches this precedent's granularity exactly (design correctly chose *not* to copy E2ETestController's environment predicate verbatim — that controller allow-lists Staging+Development, while `IsProduction()` is a deny-list; both achieve "not in Production" but the design's version is simpler and sufficient here since nothing about diagnostics needs a Staging/Development distinction).
- **`PermissionAuthorizationResultHandler.cs:42-77`** — confirmed the design's 401-vs-403 analysis: it only overrides the response body when `authorizeResult.Forbidden` is true (i.e., authenticated but under-permissioned). An anonymous caller fails authentication, not authorization-with-a-forbidden-result, so the framework's standard 401 challenge applies unmodified. The design's status-code table is accurate, not speculative.
- **`MockAuthenticationHandler.cs:38-43`** — mock-authenticated users carry both `AccessMatrix.BaseRole` ("heblo_user", verified equal to `AccessRoles.Base` via `AccessMatrix.generated.cs:6`) and `AccessRoles.SuperUser`. Confirms FR-2's acceptance criterion ("mock-auth mode continues to work") and the design's test-infrastructure-constraint claim: this handler authenticates *unconditionally* — there is no way to simulate an anonymous caller through `HebloWebApplicationFactory`, which is exactly why the design steers the new tests toward direct controller instantiation (`DashboardControllerTests` style) instead of `HebloWebApplicationFactory`.
- **`CostOptimizedTelemetryProcessor.cs:20`** — `/api/diagnostics` exclusion confirmed still present and orthogonal to this fix; correctly left out of scope.
- **Test-path precedent** — `DashboardControllerTests.cs` lives at `backend/test/Anela.Heblo.Tests/Controllers/`, but an `Anela.Heblo.Tests/API/` directory (with an existing `HealthChecks` subfolder) also exists. The design's proposed path `Anela.Heblo.Tests/API/Controllers/DiagnosticsControllerTests.cs` is not unprecedented, though the closer analog (`DashboardControllerTests`, whose direct-instantiation style the design explicitly copies) sits one level up at `Anela.Heblo.Tests/Controllers/`. This is a cosmetic filesystem-placement choice, not an architectural concern — either location is consistent with existing conventions. No action needed; noting it only so the implementer doesn't treat it as a hard requirement.

## Design decisions endorsed

1. **`[Authorize]` at class level, no custom role/policy.** Correct call to stay off `AccessRoles.generated.cs` (auto-generated, out of scope) and reuse `DefaultPolicy`. This is the same "any authenticated Base-role user" gate already used for `/mcp`, so it doesn't introduce a second gating idiom into the codebase.
2. **Per-action private-helper guard (`TryBlockInProduction`) over an `IActionFilter`.** Matches `E2ETestController`'s existing per-action-`if` idiom. Introducing a filter/attribute for a single four-action controller would be the kind of unrequested abstraction the project's coding rules explicitly discourage.
3. **Field removal, not masking/nulling, for `InstrumentationKey`/`ConnectionStringSource`.** Correct — a masked value can still leak partial key material through response-shape diffing; outright removal is the only version that satisfies "no substring of the connection string is serializable."
4. **Test strategy avoiding `HebloWebApplicationFactory`.** Justified and correct per the `MockAuthenticationHandler` finding above — there is no reasonable way to assert "anonymous → 401" through the shared factory without standing up a second scheme, which would be disproportionate. Reflection-checking `[Authorize]` presence as the proxy for framework-enforced rejection is the right level of testing (own code vs. framework behavior).
5. **Leaving `CostOptimizedTelemetryProcessor`'s `/api/diagnostics` exclusion untouched.** Correct — that exclusion is about sampling telemetry emitted by the endpoint, unrelated to gating access to it, and remains valid once the endpoint is no longer reachable anonymously.

## Risks / residual considerations (informational, not blocking)

- **Response-shape break for `appinsights-config`.** Already flagged as an open question in the plan; confirmed via grep that no frontend/script/test in this repo currently calls `/api/diagnostics/*`, so there is no known internal consumer to break. This remains a judgment call the plan already surfaced correctly — no new information changes that conclusion.
- **`ConfigureAuthorizationPolicies` runs in both mock-auth and real-auth branches** (`AuthenticationExtensions.cs:47` and `:76`), so `[Authorize]` on `DiagnosticsController` will enforce identically regardless of which auth mode is active in a given environment — no environment-specific gap here.

## Implementation guidance (unchanged from design, restated for the build step)

- Touch only `DiagnosticsController.cs` (constructor + 4 actions) and one new test file — no DI registration changes required since `IWebHostEnvironment` is already framework-registered.
- Test file: construct the controller directly (`new DiagnosticsController(logger, telemetryClient, environmentMock.Object)`), no `HebloWebApplicationFactory`. Use `Mock<IWebHostEnvironment>.Setup(e => e.EnvironmentName).Returns("Production"|"Development")` (`IsProduction()`/`IsDevelopment()` are extension methods over `EnvironmentName`, so mock the property, not the extension method).
- Verify telemetry-channel silence in the Production-guard test by wiring a real `TelemetryClient` to a `TelemetryConfiguration` with a recording `ITelemetryChannel` fake, per the design — this is the concrete regression test for the cost-mandate angle of the finding, not just an auth check.

No further architectural clarification is needed; proceed to implementation per `design-01.md`.
