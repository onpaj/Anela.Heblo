# Architecture review — `useManufacturedProductInventory` / `useMaterials` generated-client migration

## Verdict

**Approved to implement, with one clarification to fold in before coding (mutation return shape) and one out-of-scope observation.** I read the current source of both hook files, the relevant slices of `frontend/src/api/generated/api-client.ts` (lines 6749–6920, 18552–18650, 27752–28140), `docs/development/api-client-generation.md`, the `usePackingMaterials.ts` precedent, `frontend/src/api/client.ts`'s error/toast wiring, and every consumer site the plan/design named. Every factual claim in plan-01.md and design-01.md that I checked against the live code — generated method signatures, DTO field types (including the numeric→string `InventoryChangeType` drift and the `string`→`Date` field drift), the class-vs-interface literal-object call sites, the test fixture shapes, the `usePackingMaterials.ts` `new Date(date)` precedent, the toast-handling location, and the null-safety of the two `useManufacturedProductInventoryQuery` consumers — held up exactly as described. Nothing I found contradicts the design.

## Alignment with existing patterns

- **Established precedent confirmed live.** `usePackingMaterials.ts` (`frontend/src/api/hooks/usePackingMaterials.ts:69-73` and `:100-103`) already does exactly what this design proposes: `getAuthenticatedApiClient()` called with no cast, generated request classes constructed at the call site, and an explicit `date: new Date(date)` conversion rather than relying on the constructor's untyped passthrough. The design's "explicit `Date` construction at the call site" decision is not a novel choice — it is the codebase's one existing precedent for this exact date-conversion problem, applied consistently.
- **Doc rule enforcement is exact.** `docs/development/api-client-generation.md:212-215,274` bans `(apiClient as any).baseUrl`/`.http.fetch` and bare `as any` casts on the client; the design's replacement (`getAuthenticatedApiClient()` + typed generated methods, no casts) is the documented "✅ CORRECT" pattern, not the escape-hatch (`getApiBaseUrl()`/`getAuthenticatedFetch()`), which is correct here since none of these five endpoints need out-of-band status-code branching.
- **Toast/error behavior is provably unchanged.** I read `client.ts:282-374`: the global-toast and 401-redirect logic lives *inside* `authenticatedHttp.fetch`, which is the same underlying function both the old hand-rolled `apiFetch` and the new generated `process...` methods call through `apiClient.http.fetch(...)`. Swapping the call path from "manual fetch + hand-rolled `Error`" to "generated method + `ApiException`" does not change when toasts fire or what triggers the 401 redirect — only the shape of the thrown JS error object on non-2xx, and the plan's grep-verified claim that no caller string-matches `error.message` holds (confirmed no `.message ===` pattern on these two hooks' call sites).
- **Module boundary is respected.** Both files stay hook-layer modules; nothing crosses into components or the generated-client layer beyond what's already true today.

## Verified corrections/confirmations to the design

1. **Response envelope shape is real and consumers already tolerate it — no fix needed, but the design should say so explicitly.** `GetManufacturedInventoryResponse.items`/`.totalCount` are optional (`items?`, `totalCount?`) vs. the current hand-rolled type's required fields. Checked both call sites — `ManufacturedInventoryPage.tsx:294-295` (`data?.items ?? []`, `data?.totalCount ?? 0`) and `TransportBoxItems.tsx:125` (`inventoryData?.items ?? []`) — both are already optional-chaining-safe. This is a confirmed non-issue, not a gap; worth a one-line note in the design so the implementer doesn't go looking for a problem that isn't there.

2. **Mutation return-type shape change is real and *undocumented* in the design's before/after table — resolve before coding, not during.** Today `useCreateManufacturedProductInventoryItem`/`useUpdateManufacturedProductInventoryItem` return the bare item (`Promise<ManufacturedProductInventoryItem>`, from `response.json()`). The generated methods return an **envelope** — `CreateManufacturedInventoryItemResponse { item?: ManufacturedProductInventoryItemDto }` / `UpdateManufacturedInventoryItemResponse { item?: ... }` (`api-client.ts:27966-27967`, `28055-...`) — not the bare item. I checked the one consumer (`ManufacturedInventoryPage.tsx:290-291,320-325`): it only uses `onSuccess` to close the modal and relies on query invalidation for refresh; it never reads the mutation's resolved `data`. So there is **no functional regression today**, but the design should still pick a shape explicitly rather than leave it implicit, because the mutation's return type is part of this module's public interface (FR-5 promises "byte-identical" external behavior) and a future consumer could reasonably expect the bare item, matching the pre-refactor contract. **Recommendation: unwrap in the hook** — `mutationFn` should `return result.item!` (or keep `ManufacturedProductInventoryItem` as the mutation's generic return type and unwrap explicitly), not return the raw envelope. This keeps the hook's public return type stable across the refactor instead of silently narrowing it to an envelope shape nothing currently uses. One line per mutation; fold into FR-1's acceptance criteria.

3. **A third, textually-identical `(apiClient as any).http.fetch`/`.baseUrl` instance exists outside the two named files — confirmed out of scope, correctly so.** `PurchaseOrderForm.tsx:342-362` (`handleAddFromPlanningList`) duplicates `useMaterialByProductCode`'s exact hand-rolled fetch inline instead of calling the hook. It is not named in the issue evidence (which scopes to "these two part-#17 hooks") and the plan already excludes "any other `(apiClient as any)` occurrence... tracked separately per #3797/#3730." Leave it alone per the project's surgical-changes rule — flagging here only so it isn't silently rediscovered mid-implementation and scope-crept into this change. A natural (but out-of-scope) follow-up would be for that handler to just call `useMaterialByProductCode`/`useMaterialsForPurchase` instead of re-implementing it, eliminating the duplication — worth a separate issue, not this one.

4. **`AddItemToBoxInput.expirationDate` fallout is real, confirmed, and self-resolving — no design change needed.** `useTransportBoxes.ts:29,222` types `AddItemToBoxInput.expirationDate?: string` and manually serializes it into a `Record<string, unknown>` body via `JSON.stringify`. `BoxFillWorkflow.tsx:107` and `AddItemsStep.tsx:57` pass `item.expirationDate` (which becomes `Date | undefined` after this refactor) straight into that field, so `tsc` **will** flag a type mismatch, exactly as the plan predicted ("verify and fix only if tsc forces it"). I traced the consequence: `JSON.stringify` on a field holding a `Date` calls `Date.prototype.toJSON()` automatically, producing the same ISO string that was sent before — so widening `AddItemToBoxInput.expirationDate` to `Date` is a type-only fix with provably zero wire-format change. Confirms the plan's scoping decision (touch `useTransportBoxes.ts` only if `tsc` forces it, minimal fix) is correct and safe; no broader change to that file is warranted.

5. **The interface-vs-class aliasing decision is correct and necessary, not stylistic.** Verified `PurchaseOrderForm.tsx:368,423` and `CatalogAutocompleteAdapters.ts:8-19` construct plain object literals typed as `MaterialForPurchaseDto`. The generated class implements `init()`/`toJSON()` as instance methods; a plain literal without those methods fails structural typing against the class but satisfies the `I*` interface. Aliasing to `IMaterialForPurchaseDto`/`IManufacturedProductInventoryItemDto`/`IManufacturedProductInventoryLogDto` (not the classes) is required for these call sites to keep compiling, exactly as design-01.md argues.

6. **`InventoryChangeType` must be a value export, confirmed by a real runtime use.** `ManufacturedInventoryPage.tsx:30-36` builds `Record<InventoryChangeType, string>` keyed by `InventoryChangeType.InitialWriteDown` etc. — a `Record` with enum-member computed keys requires the enum object at runtime, not just its type. `export type { InventoryChangeType }` would compile-fail here; the design's plain `export { InventoryChangeType }` (value export) is required, not optional polish.

## Implementation guidance (unchanged from design-01.md, restated as the binding contract)

- `useManufacturedProductInventory.ts`: delete `getClientAndBaseUrl`, `apiFetch`, `buildFilterParams`, the hand-coded `InventoryChangeType` enum, and the `ManufacturedProductInventoryLog`/`Item`/`ManufacturedInventoryResponse` interfaces. Call `getAuthenticatedApiClient()` with no cast in each `queryFn`/`mutationFn`. Re-export `InventoryChangeType` as a value, `ManufacturedProductInventoryItem`/`Log` as type aliases to the generated `I*` interfaces. Keep `ManufacturedInventoryFilters`/`CreateManufacturedInventoryItemInput`/`UpdateManufacturedInventoryItemInput` hand-written (they are the hook's own call signature, not wire types). Convert `expirationDate` explicitly with `new Date(...)` at the create call site, matching `usePackingMaterials.ts`'s precedent. **Add:** unwrap `result.item` in both create/update `mutationFn`s so the hooks keep returning the bare item type, not the envelope (point 2 above).
- `useMaterials.ts`: delete the local `MaterialForPurchaseDto`/`GetMaterialsForPurchaseResponse` interfaces and the stale "Temporary types" comment; call `catalog_GetMaterialsForPurchase(searchTerm, limit)` directly; re-export `MaterialForPurchaseDto` as an alias to `IMaterialForPurchaseDto`; keep the client-side exact-match `.find()` filter in `useMaterialByProductCode` unchanged.
- FR-4's date-fallout file list (`ManufacturedInventoryPage.tsx` formatters, `TransportBoxItems.tsx:48`, `BoxFillWorkflow.tsx`/`AddItemsStep.tsx` via `useTransportBoxes.ts`'s `AddItemToBoxInput`, and the four test fixture files) is complete and correctly scoped — no additional files surfaced during my check of every named consumer.
- Order of work: implement the two hooks first, run `npm run build` to let `tsc` enumerate every fallout site (it will hit exactly the FR-4 list plus the `AddItemToBoxInput.expirationDate` widening), fix in place, then run the frontend unit tests for the touched components.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Mutation return-type silently narrows from bare item to envelope, surprising a future consumer even though no current one breaks | Unwrap `.item` in the two mutation `mutationFn`s (point 2) — one line each, zero behavior change today, closes the latent gap |
| `AddItemToBoxInput.expirationDate` type mismatch surfaces as a `tsc` error mid-refactor and tempts a broader rewrite of `useTransportBoxes.ts` | Confirmed minimal fix is sufficient (type widen `string`→`Date`, no serialization change) — stick to the plan's "touch only if forced, minimal fix" scoping |
| `InventoryChangeType` numeric→string swap silently breaks an out-of-repo consumer (persisted numeric value, external report) | No in-repo evidence of this; plan already flags it as an open question for the reviewer — no code action needed, just confirm with the user if they know of one before merging |
| Scope creep into `PurchaseOrderForm.tsx`'s duplicate hand-rolled fetch or other unrelated `as any` sites | Explicitly out of scope per the issue's own framing and the project's surgical-changes rule; leave as a follow-up candidate only |

## Prerequisites before implementation begins

None outstanding — no backend change needed (all five generated methods already exist and match the current hand-rolled request/response shapes byte-for-byte), no open design question blocks coding. The only action item is folding the `.item` unwrap into FR-1's mutation implementations, which is a one-line addition to the already-written design, not a redesign.
